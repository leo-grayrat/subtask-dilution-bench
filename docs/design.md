# Benchmark 设计草案

## 1. 研究问题

我们想测的不是“复杂任务里每个局部都应该做到和单独拿出来一样精致”，而是：

> **一个模型本来会做、而且局部难度没有增加的问题，放进越来越大的完整任务后，还能不能继续把它处理对？如果任务变大时允许模型使用更多 thinking / 计算资源，这种退化能不能被补回来？**

这里的 `thinking / attention` 先作为现象层面的解释，不预先声称已经知道模型内部到底发生了什么。

## 2. 不要把什么当成研究对象

### 不是“方案越复杂越好”

单独处理一个局部问题时，模型可能给出更复杂的方案；大任务里选择更简单的方法可能完全合理。因此不能用“单独版本更高级”直接判定大任务失败。

真正关心的是：某个本来需要做的判断，在大任务里是否仍然发生了，而不是最终方案是否豪华。

### 不是针对已知错误出题

`description` 被拿去数字符只是发现问题的案例，不应该变成 benchmark 的题型。不能先知道模型在哪里跌倒，再围绕这些坑设计一套测试。

### 第一版不以代码修复为主

代码任务往往有很强的即时反馈：能不能运行、测试是否通过、CI 是否全绿。模型可以通过不断“写—跑—修”把很多局部错误洗掉，这会掩盖我们真正想看的问题。

第一版更适合使用那些**局部错误不会立刻阻止任务继续完成**的任务。

## 3. 最基本的实验形状

设一个完整任务本来就包含若干要求：

`A, B, C, D, E, F ...`

我们不人工挑“最容易出错的那个”，而是让这些要求轮流成为观察对象。

以 A 为例：

- A
- A + B
- A + B + C + D
- A + B + C + D + E + F

在这些版本里，A 本身的内容、证据和难度尽量保持不变，变化的只有周围还需要同时处理多少事情。

然后对 B、C、D……重复同样的实验。

这样评价的是一个总体趋势：

> **当整体任务量增加时，原本会做的局部问题是否系统性变差。**

## 4. 单独任务的作用

单独做某个局部问题，只用于确认“这个模型本来会不会”。

如果某个模型单独处理 A 都不稳定，那么 A 对这个模型不能证明发生了“稀释”；但这不意味着要把 A 从整个数据集里永久删除，因为别的模型可能本来会。

单独版本不负责规定复杂任务里应该采用什么具体方案。

## 5. 两条运行线

### 默认运行

按照模型正常的默认方式完成不同规模的任务，观察随着任务变大，局部正确率怎么变化。

### 增加 thinking

任务越大，允许使用的推理时间、推理 token、迭代次数或子调用也随之增加，不人为把总预算固定死。

这条线用来区分几种情况：

- 默认模式下降，而增加 thinking 后明显恢复：支持“模型会，但复杂任务里没有给这个局部足够处理”的解释。
- 增加 thinking 有帮助但不能完全恢复：说明资源投入可能只是问题的一部分。
- 增加 thinking 几乎无效：说明仅用“脑力被摊薄”解释并不充分，还需要考虑任务组织、信息保持等其他问题。

## 6. 怎么评价

尽量不去判“它有没有深刻思考”，而是看可检查的局部结果。

例如：

- 是否违反一个明确条件；
- 是否把材料中的事实、时间、对象关系用错；
- 是否漏掉原任务要求中的一个必要部分；
- 是否在完整方案中破坏了一个原本能够稳定满足的约束；
- 图像里要求的人数、属性、关系是否保持正确。

核心结果至少包括：

1. 局部问题单独完成时的正确率；
2. 随整体任务规模增加，该局部问题的正确率变化；
3. 增加 thinking 后能恢复多少；
4. 整体任务本身是否仍然看起来完成得不错。

第 4 点很重要，因为我们特别关心一种情况：**整体成果还能交付，但里面一些本来会做的小问题已经明显失守。**

## 7. 当前最需要验证的事情

现在还不应该急着实现统一 evaluator 或大规模跑模型。

下一步应该先从候选 benchmark 中抽真实样例，逐条检查：

- 一道任务里是否天然有多个可以分别判断的小要求；
- 能不能自然做成较小版本、中等版本、完整版本；
- 缩小任务时，目标局部问题本身有没有被改难或改简单；
- 是否存在过强的即时反馈，让模型可以靠反复试错把错误洗掉；
- 最终局部对错能不能相对明确地判断。

只有这一步跑通，才值得继续写自动化实验框架。
