### 1.4 结构去重判定（防换皮）

按 source-selection.md 第 4.2 节的结构维度逐题比较，而非按行业名称。HANDBOOK 8 题分属金融、保险、医疗三个行业外皮，但结构维度如下：

- **主要工作载体**：除 9b2f7a29 以本地工作簿文件为主要产物（类别 1）外，其余 7 题的主要产物都落在外部工具世界（邮件、Jira、日历、付款队列），均属类别 3。
- **局部决定类型**：多为证据核对后决定处理方式（表示/建模选择与证据冲突处理的混合），外加外部状态修改；9b2f7a29 含逐项冲突判定与状态标注。
- **反馈时延**：8 题全部是延迟反馈（仅在最终评分出现），无一题具备即时反馈。这对第 3.3 节结构差异硬门槛（即时反馈至少 2 题）构成缺口，见 1.5。
- **evaluator 类型**：8 题全部为外部世界状态类评分器（verifier_code 检查外部服务 JSON 与文件）。
- **checkpoint 触发来源**：均以读取、外部结果返回与阶段交付触发。

说明：上表反馈时延指评分反馈；运行中工具调用会返回操作成功与否的结果，这属于动作层反馈，是否构成第 3.3 节意义上的即时反馈，需要在抽样框建表时逐题标注，本文不预先断言。

**去重结论（实例级已可判定的部分）**：

1. finance_meridian_partners 的 158b9045、4dace65e、a0895480 三题共享同一公司背景、同一工作载体（发票/邮件进入付款流程）、同一评分结构，高度疑似同一父模板。按第 3.4 节规则只能保留一个；保留哪一个属于抽样程序而非本文决定。
2. insurance_vanguard_shield_mutual 的 82da8d17、89007056、9b2f7a29 三题中，前两题主要产物都是外部状态（理赔处理、报销审计），9b2f7a29 主要产物是本地工作簿，结构上可区分；82da8d17 与 89007056 是否同模板需逐条比较 rubric 决策结构后判定（需要材料级细查，本轮只给出疑似结论）。
3. d9d532c1（佣金核验加多通道通信）与 f5947c33（双病案、其中一例需自行定位流程）在决定类型上与其它题有实质差异，暂判可保留。
4. 以上判定均未使用任何目标模型运行信息，符合第 4.1 节不使用目标模型筛题的要求。

### 1.5 抽样框缺口结论（如实报告）

design.md 第 3.1 节目标是 3 类任务、每类 3 个母任务、共 9 个。对照本地与限定来源的现实：

**类别 1（结构化记录与分析产物）**：本地仅 9b2f7a29 一个结构合格候选。按 source-selection.md 第 3.4 节，每类抽样框最低需 5 个合格候选，缺口至少 4 个。GAIA 中可能存在此类任务，但需材料获取实测才能确认。

**类别 2（软件仓库与多文件产物）**：本地 8 题中没有一题的主要产物是代码仓库或多文件软件产物。限定来源中唯一现实候选来源是 SWE-bench，但它同时带有强即时反馈风险（第 1.2 节）。本类别目前没有任何已判定合格的候选。

**类别 3（外部状态与多工具工作流）**：本地候选最充裕，但按第 1.4 节去重后可保留的独立结构候选约为 4 到 5 个（三题疑似同模板只保留一个、两题待细查），且每类最低仍需 5 个合格候选，缺口 0 到 1 个，取决于去重细查结果。

**来源集中度约束**：source-selection.md 第 3.4 节规定正式 9 题中同一来源集合最多占 4 个，同一类别中同一来源最多占 2 个。因此即便本地 8 题全部合格，HANDBOOK 最多贡献 4 个正式母任务，且类别 3 最多 2 个、类别 1 最多 2 个。其余至少 5 个母任务必须由 HANDBOOK 以外的限定来源（实际只剩 GAIA 与 SWE-bench 两个待实测来源）提供。

**第一部分小结**：

- 已可判定合格的母任务候选目前为 0 个：本地候选全部带有需要运行实测才能关闭的条件（即时反馈强度、环境可复现），远程限定来源尚未获取实例。
- 结构上最接近合格的候选集中在 HANDBOOK 类别 3，但受来源集中度限制最多贡献 4 题；类别 2 完全没有已判定候选；类别 1 只有 1 个结构候选。
- 缺口位置：类别 2 全缺、类别 1 缺至少 4 个抽样框候选、类别 3 缺 0 到 1 个，另需关闭全部候选的即时反馈与可复现性核查。
- 按任务要求，不建议扩源。缺口的合规出路只有两条：在既有六个限定来源内做材料获取实测（GAIA、SWE-bench 优先），或按 source-selection.md 第 3.4 节把不足类别记为尚未准备好。两条都不由本文档擅自选择，列入开放问题。
- 失败设计教训对照：本节没有围绕任何已知错误挑任务，没有把行业外皮当多样性，没有拼接小题，全部候选来自真实来源的真实任务。

## 第二部分：状态分叉方式可行性分析

design.md 第 6 节固定了三档证据强度：真实状态复制 大于 可见状态重建 大于 独立整题运行（后者不计入主 pilot）。本节按候选任务结构分析每档的技术路径、可行性依据、降级路径，并明确哪些判断必须实测。全部可行性判断均为结构推断，未经实测验证。

前置事实（均已核查）：

- HANDBOOK 候选的外部服务状态以 JSON 种子文件形式存放于 initial_external_services，运行中状态写入 /data 下服务目录，评分器从 final.json 或种子文件读取（sop_verifier.py 逻辑）。外部状态因此是完全文件化、可复制、可哈希的。
- 工作区同样是普通文件目录，可整体复制并计算逐文件 SHA-256。
- 运行载体是 Docker 容器加 harness（README 指明基于 OpenHands/software-agent-sdk 构建）。会话状态保存在进程内，是否可序列化、能否无提示暂停恢复，本地无法从文件层面判断。
- 本机没有可用 Docker/WSL（isolation-probe-2026-08-24.md），因此任何一档的实测在当前机器上都还无法开始。

### 2.1 第一档：真实状态复制（首选）

**技术路径（在 HANDBOOK 候选上具体化）**：

1. 状态组成：模型可见对话历史、工作目录文件、外部服务状态（邮件、slack、jira、日历等的 JSON 状态）、工具返回历史、已用与剩余预算、模型与工具版本。按第 6.1 节清单，这些内容在候选任务上都有明确承载物：对话在会话进程内，文件与外部状态如上所述全部文件化。
2. 分叉操作：在冻结触发条件命中时（一个工具或环境结果已写入可见历史、下一次模型调用尚未开始），对整个运行实例做检查点：导出会话对象、复制工作目录、复制外部服务状态目录、记录预算计数。
3. 三份副本分别作为 direct、sham、reconsider 的起点；启动前逐份核对第 3.2 节快照 manifest 的哈希，仅分支提示允许不同。

**可行性判断与依据**：

- 结构上有利的证据：外部状态与工作目录完全文件化（已核查），因此第一档里最难复制的通常只剩会话进程状态与外部服务的运行时实例；候选任务的评分器只看最终文件与状态，说明外部状态没有依赖隐藏持久化后端（至少本地种子文件可以完整表达初始态）。
- 结构上不确定的证据：会话进程是否暴露可序列化接口、工具连接（MCP proxy、外部 mock 服务）能否被随检查点一起冻结并复制、暂停时外部服务是否仍在后台变化，这些都不能从现有文件判断。
- 结论：第一档在候选任务上不是被结构排除，而是平台能力未知。判定为需要实测，实测项见 2.5。

### 2.2 第二档：可见状态重建（备选一）

**技术路径**：

1. 在 checkpoint 导出模型可见的完整记录：对话与工具结果文本、工作目录快照、外部服务状态快照、剩余预算数字。全部可文件化并哈希。
2. 启动三个全新会话，把同一份记录作为初始上下文注入，工作目录与外部状态从快照恢复，预算按剩余值手工设定。
3. direct 分支注入后不添加任何暂停提示；sham 与 reconsider 各注入 design.md 第 5.2、5.3 节规定的暂停提示一次。
4. 全部三分支按第 6.2 节标记为重建分叉，单独报告。

**可行性判断与依据**：

- 结构上有利的证据：需要重建的状态（对话文本、文件、外部状态 JSON、预算）在候选任务上全部可以导出为文件，重建所需原料没有结构缺口。
- 结构上的风险点：(a) 重建会话能否在不新增用户消息的情况下让 direct 分支继续（design.md 第 5 节明确，必须另发继续消息的实现不能冒充无提示 direct；重建场景下 direct 的继续同样受这条约束）；(b) 注入历史是否会被平台截断、重排序或重新包装，导致三分支可见状态名义相同实际不同；(c) 外部 mock 服务从快照恢复后，后续工具调用的返回是否与原轨迹一致；(d) 重建会话的工具权限与预算能否精确复现。
- 结论：第二档比第一档对平台要求低，但仍有多项只能实测确认。判定为需要实测，实测项见 2.5。
- 证据强度：即使实测全部通过，第二档也只能声称可见状态一致，不能声称保存了平台内部未暴露的会话状态（design.md 第 6.2 节）；必须与真实分叉分开报告。

### 2.3 第三档：独立整题运行（备选二）

design.md 第 6.3 节已固定其地位：从任务起点独立运行三条件，在冻结事件触发时分别施加条件。它技术上最容易做到（任何运行器都可以），但只能回答整套运行协议是否影响结果，不能证明同一局部状态获得 reconsider 后发生改变，不计入主 pilot 的有效母任务数，也不补足主分析最低数量。本节仅确认它在候选任务上没有额外结构障碍：三条件各自的整题运行与单次正式运行结构相同。

### 2.4 降级路径与结论强度影响
design.md 第 6 节已预先定义降级顺序。本节补充每档降级对结论边界的具体影响：
- 真实状态复制不可行，降到可见状态重建：结论从同一完整状态的分支比较退化为同一可见状态重建后的分支比较。仍可支持 reconsider 对 sham 的干预效应，但必须在报告中写明分叉方式为重建，且不能声称内部会话状态被保存。
- 可见状态重建也不可行，降到独立整题运行：只能报告整套协议层面的差异，不能作为局部可避免退化的主因果证据，不计入有效母任务数。
- 三档全部不可行：按 design.md 第 10.1 节，只报告执行协议未通过，不解释模型行为；这不构成扩题或换方法的理由。

### 2.5 必须实测才能定论的判断与最小实测清单（供用户决策）
以下判断本文档不给结论，只能由实测给出。实测全部使用不进入正式样本的练习任务，不运行正式 9 题，不作为模型行为证据。
最小实测清单：
- M1 环境可启动：选定一个候选载体（HANDBOOK 容器或等价物），确认能启动并运行一个练习任务。前置依赖：本机需要可用的 Docker/WSL/容器能力（当前没有，开放问题 Q5）。
- M2 会话可检查点：在练习任务运行到冻结事件时，能否导出完整可见状态（对话、工具结果、预算）。验证第一档的会话侧可行性。
- M3 文件与外部状态可快照：对工作目录与外部服务状态做快照、哈希、复制、恢复，确认恢复后评分器能正常运行。验证第一、二档的文件侧可行性。
- M4 三分支起点一致：对三份副本分别核对哈希，确认仅分支提示不同。验证等状态起点。
- M5 direct 无提示继续：确认所选平台能否在不新增用户消息的前提下继续 direct 分支；若必须发继续消息，按 design.md 第 5 节该实现判为不适合真实分叉，只能三分支同加恢复消息或降级。
- M6 预算可继承：确认三分支能拿到与 checkpoint 相同的剩余预算口径。
- M7 重建直连（仅第二档）：确认新会话注入历史后能继续，且历史未被截断或改写。

## 第三部分：checkpoint 触发器与状态快照 manifest 字段设计
design.md 第 4.2 节要求每个母任务在测试前写出一张 checkpoint 清单，包含 3 个主要触发条件、最多 2 个备用触发条件、每个条件的可观察事件、触发后要保存的状态、以及不触发时怎样记为缺失。experiment-records.md 第 3.2 节和第 4.3 节已经给出了编号字段。本节把两者接成两层具体的 manifest 数据结构：冻结层（运行前写死、生成哈希）与运行层（触发时填写）。本节只给字段规格，不给实现代码。

### 3.1 冻结层：每母任务的 checkpoint 触发清单
存储位置：随私有计划 manifest 一起冻结（experiment-records.md 第 3.5 节），每行一个触发条件，冻结后不可改写。每个母任务恰好 3 行 primary 加 0 到 2 行 backup。字段、类型与示例如下。
| 字段 | 类型 | 说明 | 示例 |
| --- | --- | --- | --- |
| mother_task_id | string | 稳定母任务编号，不随匿名文件名改变 | SD-T03 |
| checkpoint_id | string | 母任务内唯一触发条件编号 | SD-T03-CP2 |
| trigger_rank | enum | primary_1 到 primary_3，或 backup_1 到 backup_2 | primary_2 |
| fallback_of | string 或 null | backup 行指明替代哪个 primary；primary 行为 null | SD-T03-CP2 |
| observable_event | string | 机器可判断的事件描述，禁用需临场猜测的措辞 | 指定输入文件均已出现在读取事件且写入事件数为零 |
| event_detection | string | 判定信号来源与判定方法 | 扫描 events.jsonl 的读取与写入事件计数 |
| capture_items | string 数组 | 触发后必须保存的状态项 | conversation, workdir, external_state, tool_results, remaining_budget |
| on_not_triggered | string | 该条件未触发时怎样记为缺失 | 记为未触发，不用其它位置补位 |
| checkpoint_trigger_version | string | 触发条件文本的版本 | 2026.08.25.1 |
| checkpoint_trigger_sha256 | string | 该触发条件规范化文本的哈希 | 1f2c...(64 位) |
示例行（primary_2，某候选的第一次外部状态写入已返回条件；实际存储为标准 JSON，此处为避免格式歧义省略键值引号）：

    mother_task_id: SD-T03
    checkpoint_id: SD-T03-CP2
    trigger_rank: primary_2
    fallback_of: null
    observable_event: 首个写类工具调用（发送邮件、更新外部记录或写文件）已返回，且其后尚未出现下一个写类调用
    event_detection: events.jsonl 中第一个属于冻结写类清单的工具结果事件
    capture_items: [conversation, workdir, external_state, tool_results, remaining_budget]
    on_not_triggered: 根运行结束前未出现写类事件时记为未触发，不补位
    checkpoint_trigger_version: 2026.08.25.1
    checkpoint_trigger_sha256: 1f2c...

### 3.2 运行层：状态快照 manifest（触发时填写）
存储位置：作为 branch-groups.jsonl 对应行的状态快照部分。experiment-records.md 第 4.3 节已要求该行保存逐项 SHA-256，本节把逐项具体化为一组可核对字段。每次一个 checkpoint 实际触发就填写一份快照；未触发的条件不产生快照行，只在触发清单上记为未触发。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| snapshot_id | string | 本次状态快照唯一编号 |
| branch_group_id | string | 所属分支组，与 experiment-records.md 第 4.3 节一致 |
| checkpoint_id | string | 命中的触发条件编号，回指冻结层 |
| root_run_id | string | 所属根运行 |
| parent_run_attempt_id | string | 共同祖先尝试 |
| parent_event_index | int | 分叉边界事件索引（工具结果已写入、下次模型调用未开始） |
| fork_method_planned | enum | native_state 或 visible_state_replay |
| conversation_sha256 | string | checkpoint 前完整模型可见对话与提示的哈希 |
| workdir_manifest_sha256 | string | 工作目录文件清单（路径加逐文件哈希）的哈希 |
| external_state_sha256 | string | 各外部服务状态的逐项哈希再聚合的哈希 |
| tool_results_sha256 | string | checkpoint 前全部工具返回结果的哈希 |
| remaining_budget_action | int | 剩余动作数 |
| remaining_budget_token | int | 剩余 token 数 |
| remaining_budget_seconds | int | 剩余时间秒数 |
| model_config_id | string | 模型、参数、系统提示、工具权限的冻结配置编号 |
| pause_prompt_sha256 | string 或 null | sham 与 reconsider 的暂停提示哈希；direct 为 null |
| branch_hashes_match | bool | 三分支启动前逐项核对是否全部一致 |
| inconsistency_note | string 或 null | 不一致说明；一致时为 null |

### 3.3 manifest 如何支撑三条件等状态起点
1. 触发：冻结层清单中的某个条件由事件判定命中，运行器停在分叉边界（工具结果已写入可见历史、下一次模型调用尚未开始，design.md 第 5 节）。
2. 快照：按 3.2 字段导出并哈希全部模型可见状态，形成一份快照记录，此记录是三条件唯一的共同祖先凭证。
3. 复制与核对：生成三份副本（原生复制平台内状态，或按可见记录重建）。每份副本启动前逐项重算哈希并与快照比对，写入 branch_hashes_match；任何一项不一致即按 design.md 第 7 节判为无效分支组，不做事后补位。
4. 分支：仅允许的差异是 sham 与 reconsider 各注入一次冻结的暂停提示（pause_prompt_sha256 留证）；direct 不注入任何消息。模型版本、系统提示、工具权限、剩余预算三条件完全相同。
5. 追溯：快照记录通过 branch_group_id 与 checkpoint_id 回指触发清单与根运行，保证事后审计能还原三分支确实来自同一份可见状态。

### 3.4 与 experiment-records.md 记录格式的衔接
design.md 第 4.2 节要求的五要素（3 主 2 备、可观察事件、保存状态、缺失记法）与 experiment-records.md 的编号体系按下面方式对应，不另起一套编号：
- 冻结层触发清单的 checkpoint_trigger_version 与 checkpoint_trigger_sha256，直接填入 planned-manifest.jsonl 第 3.2 节同名字段，保证计划行能回指被冻结的触发条件文本。
- 触发条件的编号作为 decision_or_checkpoint_id 写入计划行；子任务稀释以外的研究线该字段为 null，与本清单不冲突。
- fork_method_planned 在计划行中预先写明 native_state 或 visible_state_replay，与第二部分三档一一对应；独立整题运行对应 independent_full_auxiliary 且不计入主分析。
- 运行层快照写入 branch-groups.jsonl 第 4.3 节对应行，逐项 SHA-256 即 3.2 表的 conversation、workdir、external_state、tool_results 与剩余预算字段。
- direct 分支不新建运行，复用根运行尝试在 checkpoint 之后的轨迹段，符合第 3.2 节关于 planned_branch_group_ids 的说明；sham 与 reconsider 各产生独立分支尝试。
- 未触发的条件按 on_not_triggered 记为未到达，对应第 7 节未到达字段，不自动等于无效，也不补位。
- 第 5 节分数记录要求携带共同 checkpoint 状态清单的 SHA-256，即引用 3.2 快照记录的聚合哈希，评分与快照由此挂接。
- 全部清单文件都保存在 private 目录，不进匿名包；匿名文件名与编号规则沿用第 6.1 节。

## 开放问题（仅列出，不擅自补设计）
以下是在准备过程中发现的既有设计缺口或需要决策的分支。按任务要求，本文档只列出问题，不代替决策者补写设计。

Q1 HANDBOOK 任务跨线复用的允许性。本地 8 题中 7 题（除 4dace65e 外）已是上下文整合线的冻结母任务。总账没有明文禁止同一真实任务被两条研究线用作母任务，但 design.md 第 13 节要求本线不能用上下文整合的规则题替代，且跨线复用会带来匿名包混淆、盲评材料重叠和评分器语义串扰的风险。需要决策：允许复用并规定隔离办法，还是本线排除已被上下文整合占用的任务。若排除，本地可用候选只剩 4dace65e 一题，缺口进一步放大。

Q2 类别 2 与类别 1 的候选来源。类别 2 在六个限定来源中只有 SWE-bench 一个现实方向，且带强即时反馈风险；类别 1 只有 9b2f7a29 一个结构候选。若材料获取实测后仍不足，按 source-selection.md 第 3.4 节只能把该类别记为尚未准备好。是否接受第一轮以较少类别先行，属于需要决策的设计分支，本文档不决定。

Q3 分叉平台与首选方式的冻结。design.md 第 6 节要求实验开始前为整批任务冻结首选分叉方式与降级顺序。本文档只给出三档的技术路径与实测清单，不替用户选择平台；第二部分的实测清单就是为该决策准备证据的。

Q4 练习任务的选取与预算校准。分叉可行性实测（第 2.5 节）与 256 token 暂停预算校准（design.md 第 5.4 节）都必须在不进入正式样本的练习任务上完成。练习任务从哪个来源选取、如何保证调试信息不污染正式抽样，现有文档未冻结。

Q5 运行环境能力。HANDBOOK 环境依赖 Docker 容器，本机没有可用 Docker、WSL 或容器能力（isolation-probe-2026-08-24.md 已记录）。安装容器运行时属于用户级选择，本文档不执行。在环境可用之前，第二部分的实测一项都无法开始。

Q6 被测隔离。隔离仍是三条线共同的正式阻塞。分叉正式运行要求被测实例接触不到实验仓库、评分器与条件映射；现有探针已证明当前环境不合格。本文档的 manifest 设计假设隔离问题会按既有规则单独解决，不把它的解决当作已完成。

Q7 盲评人力。软评审需要至少 2 位互不沟通的人工评审（design.md 第 8.2 节）。人力安排未定之前，软结果只能保留硬结果或标为探索性，这会影响样本量和预算规划，但不影响本文档的候选与分叉结论。

## 本文档可以支持什么、不能支持什么
可以支持：
- 在既有六个限定来源内继续做材料获取实测，因为缺口位置和候选结构已经写明；
- 为分叉平台决策准备证据，因为三档技术路径与最小实测清单已经写明；
- 在正式母任务冻结后，直接按第三部分字段填写触发清单与快照 manifest。
不能支持：
- 任何关于模型行为的结论（本文档没有运行任何模型）；
- 任何分叉方式已经可行的结论（全部标记为需要实测）；
- 正式 9 题已经可以抽样的结论（抽样框候选尚未核验完毕）。
