# 子任务稀释：参考 benchmark 与素材选择

## 1. 现成 benchmark 的角色

我们不打算让 GPT 批量生成一百个“项目”。现成 benchmark 最重要的价值是提供：

- 人类已经整理过的真实材料和任务分布；
- 比较自然的完整工作目标；
- 部分已有 gold answer、测试或 evaluator；
- 不同任务结构、材料和反馈方式带来的多样性。

我们真正新增的是**运行和对照协议**，而不是重新编一个世界。

## 2. 选择标准

候选任务优先满足：

1. 本身就是一个需要持续工作的完整任务，而不是只有最终一个选择题答案；
2. 运行过程中会自然产生多个局部判断；
3. 某个局部做差以后，整体任务仍可能继续完成，不会立刻被强反馈强制修正；
4. 至少一部分结果有外部可检查依据；
5. 可以在不改变整体目标的前提下做 checkpoint fork；
6. 不需要我们先知道“模型最可能在哪里犯错”。

第一版不做图像生成实验：成本高、评价难，而且容易引入新的视觉 evaluator 问题。

## 3. 母任务抽样框

### 3.1 先建立有限清单，再抽任务

“抽样框”不是继续在网上搜索更多 benchmark，而是在选定的来源和版本中，列出**全部满足本文件标准的候选母任务**。只有进入这张清单的任务才可能被抽中。

建立抽样框时可以阅读任务说明、官方参考答案和 evaluator，也可以检查环境能否启动，但不能先运行目标模型，再根据它容易在哪里出错决定收不收。

每个候选必须保留稳定的来源 ID。不能把一个母任务改写成多个故事后当成多个来源。

### 3.2 第一轮的三个任务类别

第一轮使用三类工作结构，每类选 3 个母任务：

1. **结构化材料与分析**：需要理解字段或材料、作出多步处理、形成分析产物；局部选择不会立即报错。
2. **多文件或仓库修改**：需要阅读多个文件、确定修改范围、实施并验证；最终有可检查产物。
3. **多工具或多来源工作**：需要在资料、工具和中间状态之间持续推进，途中自然产生多个决定。

类别按工作结构划分，不按行业名称划分。保险、医疗、零售三个故事如果都是“找到阈值后决定是否升级”，仍然属于同一种结构；数据、代码和工具任务若反馈方式与决策过程不同，才提供了更实质的差异。

若一个任务同时符合两类，在冻结前指定唯一主类别，不能为了让结果看起来跨领域而重复计入。

### 3.3 每类需要多少候选

每类抽样框目标至少有 6 个合格候选，最低不能少于 5 个。冻结时：

- 随机抽取 3 个正式母任务；
- 再随机排列至少 2 个备用母任务；
- 记录抽样程序或随机种子。

某类不足 5 个合格候选时，不从边缘任务里硬凑。该类记为尚未准备好，先解决环境或来源问题。

正式的 9 个母任务中，同一来源集合最多占 4 个；同一任务类别中，同一来源最多占 2 个。共享同一父模板、只替换数据值或故事背景的任务只能保留一个。

### 3.4 候选的入选条件

候选母任务必须同时满足：

- 原生目标本身就是完整工作，不需要我们添加“坑”才变复杂；
- 至少能预先写出 3 个自然事件型 checkpoint，其中至少 2 个预计会在多数正常运行中触发；
- 局部决定会影响后续动作或产物，但错误不一定立即终止任务；
- 至少有一部分硬结果可以复现；
- 工作目录、工具状态和模型可见对话可以复制或重建；
- 在统一预算内有现实机会完成，不是稳定超时题；
- 评分所需材料可以与被测 agent 隔离。

### 3.5 必须排除的候选

以下任务不能进入主抽样框：

- 只有一次回答、一个选择或一个最终数字的题；
- 需要设计者新加规则、异常字段或诱导描述才会出现局部判断的题；
- 正确路径每一步都被测试或环境立即强制修正，几乎没有静默局部失误空间的题；
- 必须看过目标模型轨迹才能决定 checkpoint 的题；
- evaluator 与任务说明明显冲突，或运行环境无法复现的题；
- 与另一个候选共享同一任务模板、评分逻辑和决策结构，只换了表面材料的题；
- 评分器、预期答案或实验条件无法对被测 agent 隐藏的题。

## 4. 筛选、去重与冻结流程

### 4.1 不使用目标模型筛题

筛选按下面顺序完成：

1. 固定来源名称、版本和可用任务范围；
2. 根据公开任务说明和环境结构建立候选清单；
3. 按入选和排除条件做可行性检查；
4. 按工作结构去重，而不是按故事名称去重；
5. 为每个候选写 checkpoint 和 evaluator 清单；
6. 在类别内随机抽正式任务和备用任务；
7. 生成冻结清单和哈希，再开始目标模型运行。

正式样本以外的练习任务可以用于调试复制、匿名化和评分流程。练习任务不能在调试后转入正式样本，避免调试过程中获得的信息影响选择。

### 4.2 怎样判断不是换皮

筛选者必须比较下面这些结构，而不只是题材：

- 模型主要在处理数据、文件、外部状态还是多来源证据；
- 局部决定是选择表示、确定范围、修改状态、解释结果还是安排验证；
- 错误是立即反馈、延迟反馈还是可能完全静默；
- 后续工作是否依赖前面的局部决定；
- evaluator 检查最终答案、环境状态、文件行为还是完整产物；
- 自然 checkpoint 是由读取、修改、外部结果还是阶段交付触发。

如果两项任务在这些方面基本相同，即使行业和名词不同，也按同一模板处理。分类标签的数量不能代替这种逐项比较。

### 4.3 备用任务的使用

备用任务只能在正式运行前发现环境损坏，或正式运行中母任务达不到 `design.md` 规定的最低有效运行数时，按冻结顺序启用。

不能因为正式任务的结果太容易、太难、没有出现有趣错误或不支持假设而换题。启用备用任务时必须保留原任务、失败原因和替换时间。

## 5. 当前优先参考的来源

这些都是**素材来源候选，不是已经决定整套照搬**。下一步仍需抽真实样例逐条核验。

### GAIA

用途：优先寻找比较接近真实 assistant / agent 工作的完整任务，尤其是带文件、资料、工具使用和多步处理的实例。

适合借：真实任务形态、附件和较明确的最终答案 / 验证。

注意：有些实例的局部过程并没有天然 evaluator，需要配合 checkpoint 分支和人工盲审。

参考：
- https://arxiv.org/abs/2311.12983
- https://huggingface.co/datasets/gaia-benchmark/GAIA

### LongBench v2

用途：提供真实长文档、多文档、长对话、代码仓库、结构化数据等长上下文材料。

适合借：背景材料、隐藏事实检查和长上下文压力。

注意：原始任务很多仍是问答形式，不应直接把几道题拼成“项目”；它更适合作为材料池和 hard probe 来源。

参考：
- https://github.com/THUDM/LongBench
- https://arxiv.org/abs/2412.15204

### LiveBench

用途：提供有客观 ground truth、较少依赖 LLM judge 的任务，尤其可关注 data analysis、instruction following 等部分。

适合借：硬评分、对照任务和已有 evaluator。

注意：单题本身往往不够像真实复杂项目，不作为主要生态场景来源。

参考：
- https://github.com/LiveBench/LiveBench

### SWE-bench

用途：提供真实 repository / issue 级工程任务，适合以后验证 checkpoint-fork 是否也会出现在长链代码工作中。

适合借：真实 repo、issue、测试和最终工程评价。

注意：代码测试、CI 等即时反馈很强，可能把局部错误“洗掉”，也会与“显著反馈导致资源失衡”方向发生混杂。因此不建议作为子任务稀释第一版唯一主场景。

参考：
- https://www.swebench.com/
- https://arxiv.org/abs/2310.06770

### BIG-bench / lm-evaluation-harness

用途：补充任务类型和学科多样性，或做基础能力 / 原子能力控制。

适合借：题型分布、现成实现和基础能力校准。

注意：多数原子题不适合直接当主实验；不要通过“把很多不同学科小题一起塞进去”制造所谓复杂任务。

参考：
- https://github.com/google/BIG-bench
- https://github.com/EleutherAI/lm-evaluation-harness

## 6. 暂不优先的材料

### 纯多要求指令

它们可以验证“要求越多，遵守率会不会掉”，但很容易退化成格式约束堆叠，和真实项目里的局部判断仍有距离。可以做控制，不作为唯一主证据。

### 只有最终答案的 QA / 数学题

它们适合确认某个模型原子能力，但很难观察“整体仍完成、内部局部已经失守”。

### 强即时反馈的代码环境

不是永久排除，而是第一版要谨慎，因为反复测试可能把我们最想观察的局部失误强制修正。

## 7. 候选记录与测试前检查

每个候选母任务至少记录：

- 来源名称、版本、稳定任务 ID 和许可证限制；
- 原始材料、原生任务目标、工具和交付物；
- 所属任务类别，以及与同类候选的结构差异；
- 正常完成所需的大致预算和环境依赖；
- 3 个主要 checkpoint、最多 2 个备用 checkpoint 及其机器可观察触发条件；
- checkpoint 时需要快照的对话、文件、工具状态和预算；
- 原生 hard evaluator 能覆盖什么、不能覆盖什么；
- 哪些局部只适合完整语境下的盲审；
- 是否存在过强即时反馈，以及它可能怎样洗掉局部错误；
- 使用真实分叉、重建分叉还是独立整题运行；
- 调试记录、已知环境故障和排除理由；
- 是否可能与模型训练材料重合。污染风险只作记录，不能在看过模型成绩后选择性排除。

测试前对正式 9 个母任务做一次整体核查：

1. 三个任务类别是否真的具有不同的工作和反馈结构；
2. 是否有某个来源或模板占据大多数样本；
3. checkpoint 是否都能由事件触发，而非实验员临场判断；
4. 是否至少一部分局部和最终结果有冻结的硬判据；
5. 被测 agent 是否无法访问评分器、条件映射和实验说明；
6. 正式任务、备用任务和练习任务是否已经分开；
7. 抽样、提示、预算、重复次数和停止条件是否已写入冻结清单。

这份核查通过后才能开始小规模 pilot。pilot 用于检验协议和现象，不等于正式数据集，也不用于建立排行榜。
