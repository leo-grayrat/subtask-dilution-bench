# 现有 benchmark 素材怎么用

## 1. 先看题，不先看 benchmark 名气

我们现在不是要找“最权威的 benchmark”，而是找这种材料：

> **一道完整任务本来就包含很多小要求，而且这些小要求可以分别判断有没有做好。**

这些小要求最好共同服务于一个完整目标，而不是把几道互不相关的小题硬拼起来。

还希望它满足几件事：

- 至少一部分小要求单独拿出来时并不难；
- 可以自然地减少一部分要求，做出较小版本、中等版本和完整版本；
- 缩小或扩大任务时，被观察的那个小问题本身尽量不变；
- 某个局部做错后，不会马上报错并迫使模型重做；
- 最后能比较明确地检查这个局部到底做对没有。

## 2. 怎么检查一个候选 benchmark

不能只看论文介绍。每个候选都要先抽几条真实题目，直接看数据。

对每条题做下面几件事：

1. 看原任务到底要求完成什么。
2. 把它本来就有的各项要求列出来。
3. 试着只保留其中少量要求，再逐步恢复更多要求。
4. 看这样得到的小任务、中任务、大任务是不是仍然自然，还是已经变成人工拼出来的考试题。
5. 检查同一个小要求在不同规模版本里有没有被悄悄改难、改简单或者改了含义。
6. 检查局部错误会不会立刻触发明显反馈。如果模型可以靠“做错—报错—重试”一直修到正确，这类材料不适合作为第一版主任务。

如果这些事情做不自然，那么这个 benchmark 再有名也先不用。

## 3. 不要预先找“AI 容易犯的错”

`description` 被直接拿去数字符，是发现这个问题的案例，不是出题模板。

我们不应该先总结：

- 字符串容易被乱处理；
- 某种统计量容易选错；
- 某类图像容易多手少手；

然后专门围绕这些错误设计题。

更好的做法是：一条任务本来有 A、B、C、D、E、F 六项要求，那就让 A 到 F 都轮流成为观察对象。

例如观察 A 时：

- A
- A + B
- A + B + C + D
- A + B + C + D + E + F

再换 B、C、D……重复。

这样最终看的不是某一种已知错误，而是：**任务整体越来越大以后，本来会做的小问题是否普遍更容易失守。**

## 4. 当前优先寻找的三类素材

### 多要求指令

一条任务天然同时要求模型满足多项条件，而且每项条件可以单独检查。

这类材料最适合先验证最基本的现象：要求从少到多时，原本能满足的某一项会不会开始掉。

候选：ComplexBench、InFoBench。

它们的缺点是有些要求只是格式、字数或措辞限制，所以适合做控制实验，不能单独代表真实复杂工作。

### 真实工作任务

要求模型完成一份报告、分析、方案、文档等完整成果，其中天然包含多项事实、限制和目标。

这类材料更接近我们最初观察到的问题：整体成果可能还能交付，但里面某些局部其实已经没有处理好。

候选：GDPval、ProfBench、PRBench 等。

这些名字现在都只是候选。下一步必须看真实题目后再决定。

### 多对象、多关系的图像任务

图像可以作为旁证：一个简单场景模型可能稳定画对某个对象或属性，但人物、物体、关系和剧情越来越多以后，原本会画的局部是否开始丢失。

候选：GenEval 2。

这里同样不应该专门挑“手”来测。应该利用题目本来就有的对象数量、颜色、材质、位置关系等要求。

## 5. 暂时不作为主任务的材料

### 代码修复

代码通常有很强的即时反馈：能不能运行、测试是否通过、CI 是否全绿。

这会让模型通过不断重试把很多局部错误洗掉。最后代码修好了，并不能说明复杂任务里每一步都保持了同样好的思考。

因此代码类 benchmark 可以以后作为对照，但不适合作为第一版的主要材料。

### 只有最终答案的题

如果一道题最后只有一个数字、一个选项或一个是否通过，而内部没有多个天然可检查的小要求，那么它很难直接用来研究局部能力如何随整体任务增大而下降。

这类 benchmark 最多可以用来确认某个模型单独是否具备某种基础能力，不适合直接组成主实验。

## 6. 下一步

下一步不是继续列 benchmark 名单，而是从候选中各抽几条真实样例，做一张筛选表：

- 原任务是什么；
- 里面天然有多少个小要求；
- 能不能自然缩成不同规模；
- 局部对错怎么检查；
- 有没有过强的即时反馈；
- 最后决定保留还是放弃。

只有这一步完成后，再决定第一版 benchmark 真正采用哪些素材。
