# 显著反馈导致资源失衡：实验设计

## 1. 研究问题

这个方向来自一个与“子任务稀释”不同的现象：

> **当复杂任务里的某个局部目标拥有特别清晰、连续、可验证的反馈时，模型会不会向它投入超出其全局价值的资源，挤压更重要但反馈更模糊的工作？**

CI 红 / 绿只是一个例子。真正关注的是**反馈显著性是否扭曲资源分配**。

这不是 reward hacking benchmark。模型可以完全诚实、没有作弊，却仍然因为一个局部指标太容易优化而形成 tunnel vision。

## 2. 核心区分

“有反馈以后多投入”本身不是错误。一个重要目标拥有清晰反馈时，模型理应利用它。

因此必须同时操纵两个维度：

1. **反馈显著性**：弱 / 强；
2. **局部目标的实际全局价值**：低 / 高。

形成 2×2：

| | 高价值局部目标 | 低价值局部目标 |
|---|---|---|
| 弱反馈 | 基线 | 基线 |
| 强反馈 | 应该增加投入 | 关键实验格 |

如果模型只在高价值目标上利用强反馈，这是正常资源分配；如果低价值目标也因为反馈明显而大量吸走预算，才支持“metric attraction / fixation”。

## 3. 任务要求

使用已有真实任务或已有 evaluator 的任务，不自己批量编故事。

每个任务需要：

- 一个明确的整体目标；
- 至少两个会竞争预算的局部部分；
- 可以客观评价的最终全局结果；
- 可以控制某个局部目标反馈显著性的环境；
- 总时间 / token / tool-call 预算固定或可比；
- “高价值 / 低价值”由任务目标、优先级和 evaluator 共同定义，而不是事后凭感觉宣布。

## 4. 如何操纵反馈

强 / 弱反馈尽量保持**信息内容相近**，主要改变反馈的连续性、可优化性和显著性。

例如：

- 一次性最终检查 vs 每轮给出红绿状态；
- 最终总分 vs 每轮局部实时分数；
- 模糊的完成提示 vs 明确显示还差几个失败项。

不能让强反馈条件额外获得关键事实，而弱反馈条件完全不知道结果，否则测到的是信息差，不是显著性。

## 5. 主要指标

不合成一个神奇总分，至少分别记录：

### Local Effort Share

投入到目标局部的 tool calls、tokens、迭代次数或有效操作比例。

### Global Opportunity Cost

强反馈相对弱反馈最终造成的全局任务收益变化，尤其关注低价值目标上额外投入是否挤压核心工作。

### Persistence after Diminishing Returns

局部指标已经长期无明显提升，或边际收益已经很低以后，模型仍继续投入多少操作。

### Feedback × Value interaction

核心证据不是“强反馈让模型更努力”，而是：

> **反馈强度是否在低价值局部上产生了不成比例的额外投入，而在最终全局结果上留下机会成本。**

## 6. 必要控制

1. 同任务、同总体预算或严格可比预算；
2. 强弱反馈尽量不改变事实信息量；
3. 同时存在高价值局部目标，防止把“完全不利用反馈”误判成优秀；
4. 记录完整 trajectory，而不是只看最终分数；
5. 不把“违反规则”作为必要条件，这个方向允许模型全程合规但分配失衡。

## 7. Pilot

第一版只选一个容易控制反馈的任务域即可，例如 coding / optimization 环境。

先用几十个 task-instance 检查是否真的存在稳定的 Feedback × Value interaction。如果没有，不扩展到更多领域；如果存在，再考虑数据分析、agent workflow 等场景。

## 8. 与其他方向的边界

- 与子任务稀释不同：这里局部可能不是想得太少，而是**想得太多**。
- 与上下文整合失败不同：这里未必忘记任何规则，也未必做出禁止动作。

因此单独建数据、单独评分。
