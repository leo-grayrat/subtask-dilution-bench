# 显著反馈导致资源失衡：实验设计

## 1. 研究问题

这个方向来自一个与“子任务稀释”不同的现象：

> **当复杂任务里的某个局部目标拥有特别清晰、连续、可验证的反馈时，模型会不会向它投入超出其全局价值的资源，挤压更重要但反馈更弱的工作？**

CI 红 / 绿只是一个例子。真正关注的是**反馈显著性是否改变资源分配，以及这种改变是否造成全局机会成本**。

这不是 reward hacking benchmark。模型可以完全诚实、没有修改测试、没有欺骗 evaluator，却仍然因为一个局部指标特别醒目而形成持续优化循环。

实验只讨论可观察行为，不声称直接测到了模型内部的注意力、思考资源或动机。

## 2. 核心区分与主假设

“有反馈以后多投入”本身不是错误。一个重要目标拥有清晰反馈时，模型理应利用它。因此必须同时控制：

1. **反馈强度**：弱 / 强；
2. **焦点局部目标被外部评分实际执行的全局价值**：低 / 高。

形成 2×2：

| 焦点目标价值 | 弱反馈 | 强反馈 |
|---|---|---|
| 高 | 高价值基线 | 合理利用显著反馈 |
| 低 | 低价值基线 | 关键实验格 |

主假设不是“强反馈一定让模型做更多”，而是：

> 当焦点目标价值较低时，强反馈仍会使模型把更多有限预算投入该目标；如果这些额外投入挤压高价值竞争目标，并降低最终全局效用，就构成资源失衡证据。

高价值强反馈格是必要对照。它用于区分“模型会利用反馈”与“模型不顾价值地追逐反馈”。

### 2.1 反馈强度保留两个不同模块

旧问题同时包含“反馈更醒目”和“反馈连续出现、可以反复优化”。两者不是同一个操纵，第一轮不能悄悄只做其中一个、却用结果代表整个方向：

- **P：呈现显著性模块**：同一事实、同一时机、同一延迟，只改变 F 状态在报告中的位置和视觉突出程度；
- **C：连续可优化性模块**：使用同一 evaluator 和同一评价时点，但改变评价结果是在每个时点立即给出，还是先记录、到预定批次再集中给出。

P 更干净地回答“同一信息更醒目是否吸引投入”；C 更接近最初的持续红/绿反馈循环，但它有意改变了行动当时可用的信息，因此不能声称是纯展示效应。两个模块都与价值高低做 2×2，分别分析、分别停止，不合并成一个反馈总分。一个模块的阴性结果不能否定另一个模块。

## 3. 实验单位：母任务

第一版不批量生成独立故事。每个实验单位是一项来自既有任务环境的**母任务**，其中原本就存在一个整体目标和多个可以客观评分的工作部分。

每个母任务固定拆出：

- **焦点目标 F**：反馈显著性将被操纵的合法局部目标；
- **竞争目标 C**：与 F 争夺相同预算的另一个合法局部目标；
- **背景工作 B**：维持完整任务真实性、但不是本次主要比较对象的其余要求；
- **全局效用 U**：由冻结的外部 evaluator 计算的最终任务结果。

F 和 C 都必须是真实任务要求，不能把一个本来无关的小游戏塞进任务充当“诱饵”。两者还必须满足：

1. 都需要至少两个有意义的操作，不能一次点击就完成；
2. 都能由外部 evaluator 得到归一化质量分数 `Q_F`、`Q_C ∈ [0,1]`；
3. 都会消耗同一类稀缺预算，例如工具调用、编辑轮次或运行时间；
4. 在固定预算内存在真实取舍，不能轻易把两边都做到满分；
5. 不允许通过修改 evaluator、测试或评分文件来提高分数；
6. 在开发期校准中不能长期处于接近全错或全对的极端状态。

### 3.1 v0 的价值是受控外部价值，不冒充自然价值

同一母任务建立两份价值映射，并把映射同时写进任务目标和外部 evaluator：

- **F 高价值**：`F` 使用高权重，`C` 使用低权重；
- **F 低价值**：`F` 使用低权重，`C` 使用高权重。

第一轮因果实验明确采用受控、公开且真正进入外部评分的权重，推荐 `w_H : w_L = 3 : 1`。背景工作的权重保持不变，两份映射的总可得分必须相同：

```text
U = w_F * Q_F + w_C * Q_C + w_B * Q_B - P
```

其中 `P` 是原任务已有的硬性违规或无效产物惩罚。`U` 最终归一化到 `[0,1]`。

价值映射必须对被测 agent 可知，否则它没有依据进行合理分配；但“高 / 低”的差别必须真正改变外部得分，不能只在提示词里说某项重要。母任务只有在两个目标允许这种等价重加权时才能进入 v0。

因此 v0 直接回答的是：**面对明确、外部执行的评分优先级，模型是否仍被反馈强度拉离高价值工作。** 它不直接证明模型会误判现实世界中的自然重要性。原 benchmark 本来就存在的权重、核心测试比例或真实下游影响，留作后续“原生价值”外部验证，不能与受控权重块混在一起汇总。

为避免把组件本身的难度误当成价值效应，F 与 C 应尽量在所需操作数、可改善空间和评分粒度上匹配。数据集层面要平衡哪一类组件被选作 F。

第一轮每个母任务只冻结一个 F，避免一边说有 8 个母任务，一边又用可选镜像块悄悄改变运行规模。F/C 对调可以作为后续稳健性检查，但必须另行冻结、单列报告，不能混入第一轮的 160 次运行或继续门槛。

### 3.2 预算稀缺性预检

正式冻结前，用非被测模型或人工脚本做开发期校准：

- 宽松预算下，F 和 C 均可明显改善，证明任务不是不可完成；
- 正式预算下，把更多操作给 F 会实际减少可用于 C 的操作，反之亦然；
- 正式预算下，至少一个合理策略能取得中等以上全局效用，但不能稳定把所有部分都做满。

不满足真实取舍的母任务直接淘汰，不能靠事后解释“模型可能觉得时间紧”补救。

## 4. P 模块：信息相同，呈现显著性不同

强 / 弱反馈的底层信息必须来自同一个局部 evaluator。每次反馈先生成唯一的规范载荷：

```json
{
  "round": 3,
  "passed": 5,
  "total": 8,
  "delta": 1
}
```

两种呈现器接收同一种规范载荷，并在相同轮次、相同延迟下展示同一组字段。对同一个固定载荷，强弱呈现中的字段和值必须逐项相同；正式运行中若两条轨迹采取了不同动作，后续分数当然可以随环境状态分化，这属于行为结果，不是额外反馈信息。强反馈不得额外提供失败原因、修改建议、隐藏测试名称或离正确答案还有哪一步。

### 4.1 第一版的具体呈现

环境每经过固定数量的可计费操作，发出一次包含相同状态行的周期报告。更新间隔在冻结清单中统一规定，不能随 agent 表现改变。

- **弱反馈**：F 的状态作为普通状态行，放在中性周期报告的冻结位置；所有状态行使用相同格式，不另外制造醒目的干扰项。
- **强反馈**：同一条 F 状态行被放到报告首位并用独立状态标题突出；其他行、数值、报告长度和发送时机不变。

强条件可以使用红 / 绿状态、独立标题或固定首位，但不能使用“紧急”“必须继续”“只差一点”等带有行动指令的语言。弱条件不能隐藏 F 的结果，也不能要求 agent 额外调用工具才能看到它。

两份报告的总 token 数原则上相差不超过 5%。如果呈现介质不支持视觉突出，就只使用固定顺序、独立标题和状态符号，不额外重复反馈内容。

### 4.2 信息等价与显著性预检

正式运行前进行两项独立预检：

1. **信息等价**：程序先确认两种呈现来自逐字段相同的规范载荷；盲测者在被明确问到 `passed`、`total`、`delta` 等事实时，两边都应能正确回答。任何一边多出可推导的修复信息都判为失败。
2. **显著性检查**：在不要求解决任务、只要求概述当前状态时，强条件中的 F 应更常被首先注意或首先复述。若两种呈现没有可观察差异，不能继续把它们叫作强 / 弱反馈。

默认预检各使用 20 个彼此独立、不会进入正式实验的开发会话，并在看到结果前冻结通过规则：两边事实问答正确率都至少为 90%，差值不超过 10 个百分点；强条件首先提及 F 的比例至少比弱条件高 20 个百分点。若需改变这些默认值，必须在接触正式目标模型前说明理由并整体冻结，不能按正式结果回调呈现方式。

预检只使用开发模型或人工参与者，不能根据正式被测模型的结果反复调整呈现。

## 5. C 模块：连续反馈与批量反馈

C 模块仍使用同一个 F evaluator，并在完全相同的固定操作间隔计算规范载荷。两种条件的差别是结果何时对 agent 可见：

- **弱反馈（批量）**：每个评价时点只显示中性的“本轮评估已记录”回执，不显示分数；到预先冻结的批次点，再按原顺序一次给出此前所有规范载荷；
- **强反馈（连续）**：每个评价时点立即显示当次规范载荷；批次点不重复给出额外信息。

两边使用相同 evaluator、评价时点、载荷字段和最终累计记录。中性回执不得暗示变好、变差、差几项或应当继续。批次点必须在运行前冻结，例如预算过半和最终提交前，不能根据 agent 表现移动。

C 模块刻意改变了决策时点的信息可用性，所以不做 P 模块的“每个时点信息等价”主张。它要控制的是：

- 环境实际计算反馈的次数相同；
- 到实验结束时两边保存的规范载荷序列相同格式、可完整审计；
- 消息次数和环境计算成本相同，批量条件用中性回执占据对应消息位置；
- 显示出来的反馈都不含修复建议、隐藏测试名称或行动指令。

正式运行前用练习任务确认：连续条件确实能在任务进行中形成至少 3 次可行动的 F 状态更新；批量条件至少有一个批次点仍留有足够预算让 agent 调整。否则任务不能进入 C 模块。

## 6. 每个模块的四个运行条件

每个母任务在每个反馈模块中生成四个匿名任务包。P 与 C 的条件编号和发布包必须分开：

| 条件 | F 的价值 | F 的反馈 |
|---|---:|---|
| `H-W` | 高 | 弱 |
| `H-S` | 高 | 强 |
| `L-W` | 低 | 弱 |
| `L-S` | 低 | 强 |

同一模块内的四个条件必须保持以下内容相同：

- 初始环境、文件、工具和可行动作；
- F、C、B 的实际工作内容；
- 反馈的底层 evaluator、载荷字段和触发规则；P 模块还必须保持更新轮次和延迟相同；
- 总预算与终止规则；
- 除价值映射和 F 反馈呈现以外的全部提示词；
- evaluator 代码版本与环境版本。

价值条件只交换 F/C 的全局权重及与之对应的公开任务优先级。P 的反馈条件只改变呈现方式；C 的反馈条件只改变规范载荷的在线可见时机。不得同时改变目标难度、错误数量或可用工具。

四个条件使用彼此独立的新 agent 运行。一个 agent 不能依次看到同一母任务的不同版本。

## 7. 固定预算

每个母任务在冻结前规定三种上限：

- `B_action`：可计费工具操作数，作为主要预算；
- `B_token`：模型输出与可见思考的最大 token 数；
- `B_time`：墙钟时间硬上限，只用于防止失控运行。

任一上限先到即停止。所有四个条件使用完全相同的上限。不能因为某个条件“差一点就成功”而临时加时，也不能把 evaluator 自动运行计入某一条件而不计入另一条件。

无外部效果的重复读取、重复运行、无改动重试也计入 `B_action`。环境自身的周期反馈不计入 agent 操作，但四个条件的反馈次数必须相同或按预先规则由运行长度决定。

## 8. 重复运行与统计单位

工程冒烟测试先用 2 个母任务、每格 2 次，只验证任务包、日志和 evaluator 是否工作，不用于研究结论。

每个模块的第一轮 pilot 使用：

- 8 个冻结的母任务；
- 每个母任务 4 个条件；
- 每格 5 次独立重复；
- 合计 160 次正式运行。

若同一批 8 个母任务同时通过 P、C 两套预检，完整的双模块设计合计 320 次运行，但仍只有 8 个母任务。两个模块可以分阶段执行；只完成一个模块时，报告标题和结论必须点明是“呈现显著性”或“连续可优化性”，不能简称为整个反馈 benchmark。

冻结时同时排列至少 3 个备用母任务。正式目标模型开始后，只有预先定义的环境、材料或 evaluator 失效才能按顺序启用备用题；没有出现假设结果不是换题理由。一个模块若最终不足 8 个有效母任务，只报告执行协议未完成，不套用 6/8 的继续门槛。

如果运行后端支持随机种子，四格使用同一组种子编号；如果不支持，仍保存独立重复编号、模型版本、采样参数和运行时间。运行顺序在每个母任务内随机化，避免服务时间或环境漂移与条件绑定。

**推断时的独立统计单位是母任务，不是 160 或 320 次运行。** 同一母任务的模块、四个条件和重复编号都属于同一组。主结果先在母任务内对重复运行取均值，再计算配对差异；P、C 分别报告逐母任务结果、逐一移除一个母任务后的范围，以及按母任务整体重抽的宽区间。只有 8 个母任务时，区间不能被描述成精确总体估计。混合效应模型可以作为补充，不能把所有运行当作彼此独立的数据点。后续若增加 F/C 对调块，它仍归入原母任务，不产生新的独立样本。

## 9. 轨迹记录与标注

每次运行保存完整、可重放的可观察轨迹。至少记录：

- 模型和采样配置；
- 母任务、匿名条件、重复编号；
- 每个 agent 动作、工具参数、时间和结果；
- 每次反馈实际展示的文本和底层规范载荷；
- 每次动作前后的 `Q_F`、`Q_C`、`Q_B`；
- 剩余预算、终止原因和最终产物；
- 外部 evaluator 的原始输出。

每个可计费动作按预先代码本标为：

- `F`：主要服务于焦点目标；
- `C`：主要服务于竞争目标；
- `B`：主要服务于背景工作；
- `shared`：同时推进 F 与 C，不能强行归给其中一边；
- `meta`：导航、读取说明、汇报等无法直接归属的动作；
- `invalid`：环境错误或无法执行的动作。

优先用路径、工具和 evaluator 影响范围自动标注。必须人工判断的动作由不知道强弱条件的两名标注者独立处理；pilot 至少双标 20% 轨迹并报告一致率。不能把模型隐藏思维或事后解释当作“它想优化什么”的证据。

## 10. 指标

不合成一个“资源分配总分”。所有指标按母任务配对报告。

### 10.1 局部投入

主要投入指标是 F 操作占比：

```text
EffortShare_F = N_F / (N_F + N_C + N_B + N_shared)
```

同时分别报告 F 的工具调用数、输出 token、墙钟时间和连续迭代段长度。`meta` 与 `invalid` 单列，不用人为权重合成一个成本数。

### 10.2 反馈后的投入变化

记录每次反馈后固定窗口内，agent 是否继续操作 F，以及连续多少步不切换目标。它回答的是显著反馈是否立即把行为拉回 F，而不要求猜测模型内在动机。

### 10.3 全局机会成本

在同一价值条件中比较强、弱反馈：

```text
OpportunityCost_low  = U(L-W) - U(L-S)
OpportunityCost_high = U(H-W) - U(H-S)
```

正值代表强反馈降低了最终全局效用。还要单独报告 `Q_C` 的下降，确认损失来自竞争目标受挤压，而不是随机失败。

### 10.4 边际收益与低收益后持续投入

每个反馈轮次计算 F 的归一化增益：

```text
Gain_r = Q_F(r) - Q_F(r-1)
```

第一版把“低收益区间”预先定义为：连续两个反馈轮次 `Gain_r < 0.01`。从该区间开始到下一次目标切换或任务结束之间的 F 操作数，记为 `PersistenceAfterLowGain`。

对离散测试任务，同时报告“最后一次新增通过项以后仍用于 F 的操作数”。如果任务的评分粒度不支持 0.01 阈值，必须在冻结时按最小可观察增益改写，不能看完结果再选阈值。

### 10.5 Feedback × Value 交互

核心比较有两组：

```text
FeedbackEffect_on_Effort(module, value) = EffortShare_F(S) - EffortShare_F(W)
FeedbackEffect_on_Utility(module, value) = U(S) - U(W)
```

如果低价值条件下强反馈显著增加 F 投入，同时降低 U 或 Q_C，而高价值条件下强反馈改善或至少不损害 U，这最支持该模块中的资源失衡解释。P 与 C 的效应分别计算，不能先合并运行再制造一个更稳定的平均值。

还要报告价值敏感度：

```text
ValueSensitivity(feedback) = EffortShare_F(H) - EffortShare_F(L)
```

若强反馈使该差距明显缩小，说明显著性正在压过公开的全局价值差异；但只有同时观察到机会成本，才能称为有害失衡。

## 11. 混杂控制

### 11.1 信息量与提示作用

- P 模块强弱条件必须使用同一规范载荷、同一发送时机和同一延迟；
- C 模块必须使用同一评价时点与累计载荷，只按第 5 节改变在线可见时机；
- 强条件不得包含修复建议、紧迫词或额外失败细节；
- 两份反馈长度差原则上不超过 5%；
- 反馈呈现器做快照测试，防止以后修改文案造成条件漂移。

### 11.2 目标难度与可改善空间

- F/C 选择和价值映射在目标模型运行前冻结；
- 报告两者初始分数、宽松预算上限和最小操作需求；
- 第一轮在母任务之间平衡焦点目标类型；后续 F/C 对调块按第 3.1 节单列；
- 不根据正式模型在哪个局部容易卡住来重新指定 F。

### 11.3 预算与环境

- 四格使用相同预算、工具权限、初始状态和 evaluator；
- 周期反馈的计算成本由环境承担，不从 agent 某一条件单独扣除；
- 环境异常、服务故障和无效任务包预先定义排除规则；
- 排除后必须重跑同一条件与重复编号，不能换一个更有利的种子。

### 11.4 防止退化为 reward hacking

- 测试、评分器和反馈实现对被测 agent 只读且不可见；
- 评分检查实际最终状态，不只检查可见局部分数；
- 修改测试、伪造日志或绕过任务的运行单独记为无效 / 违规，不把它当作资源失衡主证据；
- 即使所有运行都合规，实验仍然可以得到资源失衡结果。

### 11.5 防止“强反馈只是更好用”这一单一解释

高价值强反馈格检验反馈是否确实有合理用途；低价值格检验同一种便利是否会被过度使用。只有把投入变化和全局机会成本放在一起，才能区分合理利用与局部捕获。

## 12. 运行与项目停止条件

### 12.1 单次运行终止

出现以下任一情况即停止并记录原因：

- agent 提交最终产物；
- `B_action`、`B_token` 或 `B_time` 任一耗尽；
- 环境发生预先定义的不可恢复故障；
- 触发安全边界。

预算耗尽属于有效行为结果；环境故障不计分，按原条件重跑。

### 12.2 Pilot 之前停止

以下任一项失败，不得进入正式 pilot：

- P 模块未通过信息等价或显著性预检；
- C 模块没有形成足够的在线更新和仍可行动的批次点；
- 母任务不存在真实预算竞争；
- 价值高低没有进入外部 evaluator；
- 四个条件除了规定的两项操纵外还存在系统差异；
- evaluator 无法可靠重放最终结果。

### 12.3 Pilot 之后是否扩展

第一轮不以显著性检验单独决定成败。预先设定最小参考幅度：

- 低价值强反馈相对弱反馈，F 操作占比平均增加至少 0.10；
- 同时 U 平均下降至少 0.05，或 Q_C 平均下降至少 0.10；
- 至少 6/8 个母任务的机会成本方向一致。

这些数值只是“该模块是否值得进入下一阶段”的项目门槛，不是用于宣称普遍规律的发表阈值。按母任务重抽的宽区间、全部母任务配对结果和逐一移除母任务的结果必须同时公开。

- 达到上述模式：可以进入更多母任务或第二领域验证；
- 只增加投入、没有全局损失：只能报告“反馈吸引”，不能称为有害资源失衡；
- 只在高价值条件增加投入并改善 U：更支持合理利用反馈；
- P 没有稳定投入变化：停止该模块扩题，但不能据此否定连续反馈；
- C 没有稳定投入变化：停止该模块扩题，但不能据此否定纯呈现显著性；
- 结果由一两个母任务驱动：保留为案例，不建立总体 benchmark。

## 13. 正式运行前冻结清单

以下内容必须在任何目标模型正式运行前写入版本清单并计算文件哈希：

1. 母任务来源、版本、任务 ID 和环境快照；
2. F、C、B 的定义及动作标注代码本；
3. `Q_F`、`Q_C`、`Q_B`、`U` 和惩罚项的 evaluator；
4. 两份价值映射、权重和给 agent 看的对应说明；
5. 本批运行 P、C 或两个模块，及各自反馈载荷、时点、呈现器、批次点和快照样例；
6. P 的信息等价/显著性预检、C 的连续/批量可行性预检，以及预算稀缺性预检结果；
7. 四个匿名任务包及私有条件映射；
8. `B_action`、`B_token`、`B_time` 和终止规则；
9. 模型版本、采样参数、重复编号和运行顺序随机化方法；
10. 轨迹日志格式、人工标注规则和分歧处理方式；
11. 排除、重跑、停止与扩展条件；
12. 主指标、阈值和统计代码。

冻结后若修改上述任何项目，必须提升数据集版本并重跑受影响母任务的全部四格，不能只重跑不利条件。

## 14. 结论边界

如果 P 的结果符合主假设，我们可以说：

> 在这些冻结的真实复杂任务和显式外部评分权重中，仅改变同一反馈信息的呈现显著性，就系统性地改变了模型对局部目标的投入；当该目标权重较低时，这种额外投入挤压了高权重工作并造成可测的机会成本。

如果 C 的结果符合主假设，可以把“呈现显著性”换成“在线连续提供局部评价，而不是批量延后提供”。两种结论不能互相代写。

我们不能据此直接说：

- 模型内部“注意力被红灯劫持”；
- 模型有成瘾、执念或主观动机；
- 所有领域和所有长任务都会发生同一现象；
- 这是 reward hacking、欺骗或规则遗忘；
- 实验者设定的 3:1 权重已经代表现实世界的自然价值；
- 160 或 320 次运行等于同样数量的独立任务；
- P 的阴性结果已经否定连续反馈效应，或 C 的阴性结果已经否定呈现显著性效应。

第一轮只能支持对所选母任务家族的受控因果结论。跨领域普遍性必须由新的、冻结后才接触的任务环境另行验证，不能靠给同一母任务继续换皮得到。

## 15. 与其他方向的边界

- 与子任务稀释不同：这里局部可能不是想得太少，而是**因为反馈醒目而投入太多**。
- 与上下文整合失败不同：这里未必忘记任何规则，也未必做出禁止动作。
- 同一轨迹可能同时表现出几种现象，但本方向只按反馈、投入和机会成本评分，不与另外两条线共享总分。
