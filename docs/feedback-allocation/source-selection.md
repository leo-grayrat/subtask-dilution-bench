# 显著反馈导致资源失衡：参考资料与素材选择

## 1. 主要参考谱系

这个方向最接近 reward hacking / specification gaming / optimization-pressure 一类工作，但研究问题不同。

我们借的是：

- 连续反馈怎样塑造 trajectory；
- 如何逐轮记录模型从正常优化进入局部目标捕获；
- 如何只修改环境反馈而尽量保持原任务不变。

我们不把“模型是否作弊”作为主问题。

## 2. Reward Hacking Benchmark（RHB）

用途：参考**连续可见反馈 + 多轮优化压力**的实验形状。

尤其值得借：

- 每轮都能看到局部表现；
- 观察行为随迭代轮数变化，而不是只测一次；
- 对不同反馈 / sandbox 条件做干预。

我们需要改造的地方：把“是否 exploit evaluator”换成“是否对低全局价值的显著指标持续投入过多资源”。

当前作为方法参考，不直接把它的数据当最终数据集。

参考：
- https://kunvarthaman.com/posts/rhb-v1.html

## 3. EvilGenie

用途：参考**从已有编程 benchmark 出发，只改变评价环境和可利用反馈**，而不是重新生成一套人工故事。

尤其值得借：

- 使用成熟 coding 任务作为底座；
- 保留 hidden tests / 外部检查；
- 完整记录 agent 在可见评价信号下的行为。

我们需要改造的地方：不诱导 hard-code、改测试等 hacking，而是让一个合法但低价值的局部指标变得特别可优化，测机会成本。

参考：
- https://github.com/JonathanGabor/evilgenie_inspect

## 4. 后续素材选择标准

候选 benchmark / environment 应满足：

1. 有真实、外部可验证的整体目标；
2. 可以把最终效用拆成至少两个竞争资源的部分；
3. 至少支持一种冻结模块：在不改变反馈事实、更新时机和延迟的前提下控制呈现显著性，或用同一 evaluator 控制评价结果是连续在线显示还是批量延后显示；
4. 能记录 tokens / tool calls / 迭代次数；
5. 同一任务可做强反馈和弱反馈配对；
6. 高价值和低价值局部都能构造，防止把“追反馈”本身定义成坏事。

这里的“能构造”不是让 AI 另写一段业务故事，而是原任务中本来就存在两个可以独立评分、会竞争同一预算的局部目标。候选任务还必须允许：

- 对焦点目标只按所选模块改变反馈呈现或在线可见时机，不改变 evaluator 和规范载荷；
- 用外部 evaluator 交换焦点目标和竞争目标的受控评分权重；
- 在相同固定预算下形成可验证的取舍；
- 保存动作级 trajectory，并把操作归到两个目标或背景工作；
- 四个条件共享同一初始状态、工具和最终评分代码。

如果只能给某个局部加一句“它不太重要”，却不能让最终效用真正体现价值差异，该任务不进入第一版。受控评分权重测的是对明确外部优先级的资源分配，不冒充任务在现实世界中的自然价值。

## 5. 暂不优先

### 只有一个最终分数的 benchmark

无法研究资源到底被哪个局部吸走。

### 纯 reward hacking 场景

如果唯一失败就是“为了拿高分作弊”，会把我们的问题重新变成 alignment / hacking，而不是资源分配。

### 人工声明“这个局部不重要”的故事

全局价值应该由任务目标和 evaluator 真实体现，不能只靠提示词说“这个不重要”。

## 6. 下一步

不再扩展来源清单。只在 RHB / EvilGenie 的公开实现及其已有底层任务中检查母任务候选，先验证我们能否做到：

- 保持任务本体不变；
- 找到两个原生、可评分、会竞争预算的局部目标；
- 为 P 模块用同一规范载荷制作信息等价的强 / 弱呈现，或为 C 模块制作同一评价序列的连续 / 批量反馈；
- 用外部 evaluator 而不是提示词清楚执行高 / 低评分价值；
- 在固定预算内证明存在真实机会成本；
- 最终用 opportunity cost 而不是主观评价判定是否失衡。

第一轮只需要得到少量通过上述检查的母任务。若现有来源无法同时满足至少一个反馈模块和外部价值交换，应停止并报告素材不适配，而不是继续搜索新 benchmark 或让 AI 自由生成任务。只通过 P 或只通过 C 时必须按模块命名结果，不能把未实现的另一种反馈也算作已经测试。
