# 显著反馈导致资源失衡：参考资料与素材选择

## 1. 主要参考谱系

这个方向最接近 reward hacking / specification gaming / optimization-pressure 一类工作，但研究问题不同。

我们借的是：

- 连续反馈怎样塑造 trajectory；
- 如何逐轮记录模型从正常优化进入局部目标捕获；
- 如何只修改环境反馈而尽量保持原任务不变。

我们不把“模型是否作弊”作为主问题。

## 2. Reward Hacking Benchmark（RHB）

用途：参考**连续可见反馈 + 多轮优化压力**的实验形状。

尤其值得借：

- 每轮都能看到局部表现；
- 观察行为随迭代轮数变化，而不是只测一次；
- 对不同反馈 / sandbox 条件做干预。

我们需要改造的地方：把“是否 exploit evaluator”换成“是否对低全局价值的显著指标持续投入过多资源”。

当前作为方法参考，不直接把它的数据当最终数据集。

参考：
- https://kunvarthaman.com/posts/rhb-v1.html

## 3. EvilGenie

用途：参考**从已有编程 benchmark 出发，只改变评价环境和可利用反馈**，而不是重新生成一套人工故事。

尤其值得借：

- 使用成熟 coding 任务作为底座；
- 保留 hidden tests / 外部检查；
- 完整记录 agent 在可见评价信号下的行为。

我们需要改造的地方：不诱导 hard-code、改测试等 hacking，而是让一个合法但低价值的局部指标变得特别可优化，测机会成本。

参考：
- https://github.com/JonathanGabor/evilgenie_inspect

## 4. 后续素材选择标准

候选 benchmark / environment 应满足：

1. 有真实、外部可验证的整体目标；
2. 可以把最终效用拆成至少两个竞争资源的部分；
3. 可以控制某个局部反馈的显示频率、显著性或连续性；
4. 能记录 tokens / tool calls / 迭代次数；
5. 同一任务可做强反馈和弱反馈配对；
6. 高价值和低价值局部都能构造，防止把“追反馈”本身定义成坏事。

## 5. 暂不优先

### 只有一个最终分数的 benchmark

无法研究资源到底被哪个局部吸走。

### 纯 reward hacking 场景

如果唯一失败就是“为了拿高分作弊”，会把我们的问题重新变成 alignment / hacking，而不是资源分配。

### 人工声明“这个局部不重要”的故事

全局价值应该由任务目标和 evaluator 真实体现，不能只靠提示词说“这个不重要”。

## 6. 下一步

从 RHB / EvilGenie 的公开实现和其底层任务中抽真实样例，先验证我们能否做到：

- 保持任务本体不变；
- 只改变局部反馈显著性；
- 清楚定义高 / 低全局价值；
- 最终用 opportunity cost 而不是主观评价判定是否失衡。
