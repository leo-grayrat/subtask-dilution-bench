# 反馈分配线来源差距分析

更新日期：2026-08-25

状态：仅设计核查。本文件不修改 `design.md` 与 `source-selection.md`，不运行任何实验或模型，只分析本仓库中已记录的信息。不探测、不核实任何外部资源；凡需要核实的外部属性，一律列入第 3 节“实测建议清单”。

## 0. 范围与依据

- 限定来源范围：`source-selection.md` 第 6 节写明不再扩展来源清单，只在 RHB / EvilGenie 的公开实现及其已有底层任务中检查母任务候选；`pre-test-readiness.md` 第 3 节确认该范围。
- 准入标准：集中在 `source-selection.md` 第 4 节的六条，另有 `design.md` 第 3、3.1、3.2 节的补充条款。
- 停止规则依据：`source-selection.md` 第 6 节、`pre-test-readiness.md` 第 3 节、`design.md` 第 12.2 节。
- 计数说明：任务口径称“五条素材准入标准”，`source-selection.md` 第 4 节实际记录六条；本文按六条全部核对，避免漏条。

## 1. 准入标准清单化

### 1.1 主清单：`source-selection.md` §4 六条（必须同时满足）

| 编号 | 标准 | 判定依据要求 |
|---|---|---|
| S1 | 有真实、外部可验证的整体目标 | 需说明来源对最终产物有外部、可独立执行的评分或验证，而不是模型或实验者自报分数 |
| S2 | 可以把最终效用拆成至少两个竞争资源的部分 | 需指出原任务中本来就存在、可独立评分、消耗同一预算的两个局部目标；不得塞入诱饵（对应 `design.md` §3） |
| S3 | 至少支持一种冻结模块 | P 模块：在不改变反馈事实、更新时机和延迟的前提下控制呈现显著性；或 C 模块：用同一 evaluator 控制结果是连续在线显示还是批量延后显示。需要来源的反馈通道可被受控改造 |
| S4 | 能记录 tokens / tool calls / 迭代次数 | 需有动作级轨迹采集口径，能把操作归到 F / C / B（对应 `design.md` §9 标注） |
| S5 | 同一任务可做强反馈和弱反馈配对 | 需要同一母任务、同一初始状态与工具，只改变反馈呈现或在线可见时机（对应 `design.md` §6 四条件） |
| S6 | 高价值和低价值局部都能构造 | 价值差异必须真正进入外部评分权重，不能只在提示词里说某项不重要（对应 `design.md` §3.1 与 `source-selection.md` §4 末段） |

### 1.2 补充条款（`design.md` §3、§3.1、§3.2 与 `source-selection.md` §4 补充段）

主清单之外，候选母任务还必须同时满足下列条款，任一不满足同样淘汰：

| 编号 | 条款 | 出处 |
|---|---|---|
| D1 | F 与 C 都必须是原任务本来就有的真实要求，各需至少两个有意义操作 | `design.md` §3 |
| D2 | F、C 都能由外部 evaluator 得到归一化质量分数 | `design.md` §3 |
| D3 | F、C 消耗同一类稀缺预算，固定预算内存在真实取舍（预算稀缺性预检） | `design.md` §3、§3.2 |
| D4 | 不允许通过修改 evaluator、测试或评分文件提高分数 | `design.md` §3、§11.4 |
| D5 | 两个目标允许 3:1 等价重加权，且两份价值映射总可得分相同 | `design.md` §3.1 |
| D6 | 四个条件共享同一初始状态、工具和最终评分代码；动作级 trajectory 可保存并归到两个目标或背景工作 | `source-selection.md` §4 补充段 |

## 2. 逐来源差距分析

### 2.0 限定来源清单与判定前提

`source-selection.md` 中记录的限定来源只有两个：

| 来源 | 记录位置 | 文档定位 |
|---|---|---|
| Reward Hacking Benchmark（RHB） | §2 | “当前作为方法参考，不直接把它的数据当最终数据集” |
| EvilGenie | §3 | “参考从已有编程 benchmark 出发，只改变评价环境和可利用反馈” |

此外 §6 写明实际候选池是“RHB / EvilGenie 的公开实现及其已有底层任务”，但仓库中**没有记录任何一个具体底层母任务的名称、版本或核验结果**。§5 另列了三类“暂不优先”的排除项（见 §2.3）。

判定前提（必须遵守，否则会越证据）：本文作者**没有访问外部仓库、没有运行任何来源的评测**，只能依据 `source-selection.md`、`design.md`、`research-ledger.md`、`pre-test-readiness.md` 中已写明的文字判定。凡是文档没有写明的属性，一律标“无法从文档判定（需实测）”，不得写成“满足”或“不满足”。以下逐条结论都受这一前提约束。

### 2.1 Reward Hacking Benchmark（RHB）

| 标准 | 判定 | 依据（均为仓库文档原文） |
|---|---|---|
| S1 真实外部可验证整体目标 | 无法从文档判定（需实测） | §2 只记录其形状是“连续可见反馈 + 多轮优化压力”，关注点是“是否 exploit evaluator”，没有记录其底层任务是否存在我们意义上的真实整体目标；且 §2 明确“不直接把它的数据当最终数据集” |
| S2 拆成至少两个竞争资源的部分 | 无法从文档判定（需实测） | 文档没有记录任何底层任务含两个可独立评分、会竞争同一预算的局部目标；§6 把“找到两个原生、可评分、会竞争预算的局部目标”列为待验证项，说明尚未确认 |
| S3 支持一种冻结模块 | 无法从文档判定（需实测） | §2 记录可“对不同反馈 / sandbox 条件做干预”，形状上接近 C 模块（连续反馈）；但能否在不改反馈事实与时机的前提下实现 P 的等值信息呈现，文档未记录 |
| S4 记录 tokens / tool calls / 迭代 | 无法从文档判定（需实测） | §2 只记录“观察行为随迭代轮数变化”，即迭代轮次有口径；逐动作的 tokens / tool calls 是否可采集未记录 |
| S5 同一任务可做强弱反馈配对 | 无法从文档判定（需实测） | §2 提到可对反馈条件做干预，但没有记录同一母任务能生成信息等价、仅呈现不同的强 / 弱两版 |
| S6 高 / 低价值局部都能构造 | 无法从文档判定（需实测），且文档明示需改造 | §2 写明“需要改造：把‘是否 exploit evaluator’换成‘是否对低全局价值的显著指标持续投入过多资源’”；价值权重进入外部评分这一要求（`design.md` §3.1）在文档中没有任何已实现的记录 |

**RHB 结论标签：需实测验证。**

两条额外的结构性风险（来自文档原文，不是外部核实结果）：

1. **定位冲突**：`source-selection.md` §2 自己写明“当前作为方法参考，不直接把它的数据当最终数据集”。也就是说，即便实测通过，RHB 的**现成数据也不能直接当母任务集**，只能借其反馈形状；这与“找到真实环境直接跑”的预期存在距离。
2. **与排除项擦边**：§5 把“纯 reward hacking 场景（唯一失败是‘为了拿高分作弊’）”列为暂不优先，理由是会把问题拉回 alignment / hacking。RHB 字面上正是 reward hacking benchmark。它是否属于这条排除项，取决于其实测底层任务是否还有“合法但低价值的局部目标”——这一点文档没有回答，只能实测。

### 2.2 EvilGenie

| 标准 | 判定 | 依据（均为仓库文档原文） |
|---|---|---|
| S1 真实外部可验证整体目标 | 满足（有文档支持，仍需实测确认粒度） | §3 记录其“保留 hidden tests / 外部检查”，即存在外部可执行的检查；但这只是“有外部检查”，是否构成我们要求的单一真实整体目标，仍取决于底层任务 |
| S2 拆成至少两个竞争资源的部分 | 无法从文档判定（需实测），且是本来源最薄弱的一条 | §3 只记录“使用成熟 coding 任务作为底座”。成熟 coding 任务的常见形态是“通过一组测试”，天然是**单一聚合分数**，与 §5 排除的“只有一个最终分数的 benchmark”形状接近；文档没有记录任何一个底层任务含两个可独立评分、会竞争同一预算的局部目标 |
| S3 支持一种冻结模块 | 无法从文档判定（需实测） | §3 记录“只改变评价环境和可利用反馈，而不是重新生成一套人工故事”，方向上与我们“只改反馈、尽量不动原任务”一致；但能否实现 P 的等值呈现或 C 的连续/批量切换，文档未记录 |
| S4 记录 tokens / tool calls / 迭代 | 无法从文档判定（需实测） | §3 记录“完整记录 agent 在可见评价信号下的行为”，但是否细到逐动作 tokens / tool calls 未记录 |
| S5 同一任务可做强弱反馈配对 | 无法从文档判定（需实测） | §3 记录其在“可见评价信号”下记录行为，说明反馈通道可被操纵；但没有记录同一任务能产出信息等价、仅呈现或时机不同的强 / 弱两版 |
| S6 高 / 低价值局部都能构造 | 无法从文档判定（需实测），且文档明示需改造 | §3 写明“需要改造：不诱导 hard-code、改测试等 hacking，而是让一个合法但低价值的局部指标变得特别可优化，测机会成本”；受控权重进入外部评分（`design.md` §3.1）没有任何已实现记录 |

**EvilGenie 结论标签：需实测验证。**

说明：上表中 S2 一行含有推理成分——“成熟 coding 任务常为单一聚合分数”是对编程类任务一般形态的推断，不是仓库记录的结论，实测时必须用真实任务结构检验；若实测发现底座任务确有多组件、可独立评分且竞争预算的结构，该行改判为满足。

### 2.3 “暂不优先”排除项与候选池缺口

`source-selection.md` §5 列出的三类排除项不属于候选环境，仅在此登记，防止以后被重新捡回：

| 排除项 | 不满足的标准 | 可否通过改造满足 |
|---|---|---|
| 只有一个最终分数的 benchmark | S2（无法研究资源被哪个局部吸走，§5 原文） | 否。单一分数是其固有结构；为它补充分项评分等于新造 evaluator，违反“真实环境”与 `design.md` §3 的原生要求 |
| 纯 reward hacking 场景 | 研究问题边界：唯一失败若是作弊，问题退回 alignment / hacking（§5 原文） | 否。改造方向与本研究问题冲突；`design.md` §1、§11.4 明确要求实验不测作弊 |
| 人工声明“这个局部不重要”的故事 | S6 与 `design.md` §3.1：价值必须由任务目标和外部 evaluator 真实体现 | 否。靠提示词声明价值正是被明文禁止的替代方案 |

**候选池缺口（本线最大的记录空白）**：§6 把检查范围定为“RHB / EvilGenie 的公开实现及其已有底层任务”，但仓库中没有任何一条记录给出具体底层任务名称、任务结构、评分粒度或适配检查结果。也就是说：当前连“候选母任务清单”都不存在，遑论合格母任务。这与 `pre-test-readiness.md` §3 的“找到至少一个符合要求的真实环境和母任务：未完成，正式阻塞”一致。

## 3. 实测建议清单

以下动作全部留给用户在自己愿意时执行；本文作者未执行、也不应代为执行任何外部探测。每项给出：验证什么问题、验证动作、预期看到什么算通过。顺序即建议优先级。

### 实测 1（最高优先级）：在 EvilGenie 底座中找一个含两个竞争局部的任务

- **验证什么问题**：S2 + D1/D2/D3——是否存在原生、可独立评分、竞争同一预算的两个局部目标。
- **验证动作**：阅读 EvilGenie 公开实现（`source-selection.md` §3 给出的仓库链接）所用的底座编程任务清单，任选若干任务，检查其评分是否可拆成至少两组彼此独立、各自需要多步操作、且共享同一预算的部分（例如两个相互独立的功能模块测试组）。不需要运行模型，只做任务结构检查。
- **通过标准**：至少一个任务能指认 F 与 C 两个原生部分，各自至少两个有意义操作，各自可得到 [0,1] 归一分，且在固定预算内不能轻易两边满分（对应 `design.md` §3、§3.2）。找不到则该任务淘汰，不能靠事后解释补救（§3.2 原文）。

### 实测 2：确认 EvilGenie 的整体目标是外部可执行评分

- **验证什么问题**：S1 + D2/D4——hidden tests / 外部检查是否真的能在不依赖模型自报的情况下重放，且被测端无法改写。
- **验证动作**：按其文档运行一次官方评测（不接被测模型，用其自带样例或人工产物即可），确认评分由外部检查产出、检查文件对被测端只读。
- **通过标准**：同一产物两次评分一致；评分逻辑不在被测端可写路径内（对应 `design.md` §11.4）。

### 实测 3：验证反馈通道可被受控改造（P 或 C 至少一个）

- **验证什么问题**：S3——能否在不改变反馈事实、时机、延迟的前提下改呈现（P），或用同一 evaluator 控制在线 / 批量（C）。
- **验证动作**：找到其把评价结果交给 agent 的那一段代码或输出格式，确认存在一个可被我们替换 / 包装的“呈现层”，而底层规范载荷与计算时机不动。
- **通过标准**：强弱两版能共享同一份逐字段相同的规范载荷（P，`design.md` §4），或同一评价序列只改可见时机（C，§5）。若呈现与计算写死在一起、无法分离，则该来源对相应模块判不满足。

### 实测 4：验证动作级轨迹可采集

- **验证什么问题**：S4 + D6——tokens / tool calls / 迭代次数能否逐动作记录并归到 F / C / B。
- **验证动作**：查看其运行记录或日志格式，确认每个工具调用都有可导出的参数、时间与结果；若只记录轮次汇总，则不满足。
- **通过标准**：能导出逐动作序列，且每个动作可被标注到 F / C / B / shared / meta（`design.md` §9）。

### 实测 5：验证价值权重可交换且总可得分相同

- **验证什么问题**：S6 + D5——能否为同一母任务建立两份价值映射，把 3:1 权重真正写进外部评分，且两份映射总可得分相同。
- **验证动作**：在实测 1 找到的候选任务上，草拟 `U = w_F*Q_F + w_C*Q_C + w_B*Q_B - P` 的两份权重表（`design.md` §3.1），检查背景工作权重不变、总可得分一致，且权重差异对被测 agent 公开可知。
- **通过标准**：两份映射都能落到同一个外部评分代码里，而不是只改提示词（`source-selection.md` §4 末段明令禁止后者）。

### 实测 6：先判定 RHB 是否落入 §5“纯 reward hacking”排除项

- **验证什么问题**：RHB 的底层任务中，唯一失败模式是否就是“为了拿高分作弊 / exploit”。
- **验证动作**：阅读 RHB 公开说明与任务样例（`source-selection.md` §2 给出的链接），检查其任务是否保留合法的、非作弊的工作内容，以及“不做 exploit 也能得到部分分”的空间。
- **通过标准**：存在合法工作目标与可被正当优化的局部，才继续实测 7；若唯一有意义的行为差异就是作弊与否，按 §5 直接淘汰并记录，不再投入。

### 实测 7：在 RHB 底层任务中重复实测 1 与实测 3

- **验证什么问题**：S1/S2/S3——RHB 底层任务是否有真实整体目标、两个竞争局部，以及反馈通道可否受控改造。
- **验证动作**：对通过实测 6 的任务，重复“找两个竞争局部”与“分离呈现层”两项检查；注意 §2 写明只借形状、不直接用其数据，因此必须确认底层任务本身是真实任务，而不是为测 exploit 人工搭的壳。
- **通过标准**：同实测 1 与实测 3 的通过标准。若底层任务只是 exploit 演示壳，则不满足“真实环境”要求，判不合格。

### 实测 8：规模可行性（通过前述实测后才做）

- **验证什么问题**：合格来源能否提供足够母任务。
- **验证动作**：在通过实测 1–5 的来源中清点结构相似但彼此独立的候选任务数量，对照 `design.md` §8 的“8 个冻结母任务 + 至少 3 个备用”。
- **通过标准**：候选数明显多于 11；若只有 1–2 个任务通过，只能说明存在现象级样例，不足以支撑该模块的冻结清单，需按停止规则与重大分支处理，而不是放宽标准凑数。

### 实测之外的前置条件提醒

即使上述实测全部通过，本线仍受共同门槛阻塞：被测实例隔离未解决（`pre-test-readiness.md` §1）、呈现器与预检未实现、动作级采集未实现。来源适配只是众多阻塞中的第一个。

## 4. 结论与停止规则对照

### 4.1 结论标签一览

| 来源 / 类别 | 结论标签 | 一句话依据 |
|---|---|---|
| RHB | 需实测验证 | 六条标准中五条无法从文档判定；且 §2 明示不直接用其数据、与 §5 排除项存在擦边风险 |
| EvilGenie | 需实测验证 | S1 有文档支持；S2 是最薄弱且无法从文档判定的一条；其余均需实测 |
| 底层任务候选池 | 无记录（缺口） | 仓库没有任何具体候选母任务的记录，连清单都不存在 |
| §5 三类排除项 | 不合格（规则层面） | 单一分数、纯 hacking、提示词声明价值，均被明文排除且不可通过合规改造满足 |

按当前信息，**没有任何来源可判“合格”**；也没有任何一个候选来源可判“不合格”——两个限定来源都处于证据空白状态。

### 4.2 当前是“有活路”还是“接近触发停止规则”

结论：**形式上有活路，实质上已非常接近触发停止规则。**两条判断都给出依据，不粉饰。

**“有活路”的依据**：`source-selection.md` §6 的停止条件是“现有来源**无法**同时满足至少一个反馈模块和外部价值交换”才停止。当前证据状态是“尚未验证”，不等于“无法”。因此两个限定来源仍是名义上的候选，实测是唯一未被明文关闭的通道。

**“接近触发停止规则”的依据**：

1. 设计文档 `design.md` 已把实验规格写到 410 行的可执行级别，但**连一个具体底层母任务的名字都没有记录**。差距不在“还差几步工程”，而在“对象是否存在”这一前提本身。
2. 六条准入标准里，两条来源各有至少五条无法从文档判定，且两个来源都自带结构性风险（RHB 定位冲突 + 擦边排除项；EvilGenie 的 S2 薄弱）。实测不通过的概率不是小概率事件。
3. `research-ledger.md` 第 9 条与 `source-selection.md` §6 都写明“素材不合格不强行推进、无信号不扩题”。一旦实测返回否定，本线必须停止，而不是找新来源或让 AI 编任务补洞。

### 4.3 停止规则的触发路径与“部分终止”判断依据

- 若实测 1–3 对 EvilGenie 失败（底层任务拆不出两个竞争局部，或反馈通道无法与评分计算分离），且实测 6–7 对 RHB 同样失败：按 `source-selection.md` §6 原文“应停止并报告素材不适配，而不是继续搜索新 benchmark 或让 AI 自由生成任务”，本线 pilot 终止。
- 若只有一个模块可行（例如只能做 C、做不了 P）：不整体停止，按 §6 末段以窄模块命名继续，另一模块不计入。
- “该线可能部分终止”的判断依据：`pre-test-readiness.md` §5 重大分支 3 写明“RHB / EvilGenie 中有合格任务则继续；没有则停止该 pilot。启用新来源属于新的设计审查，不是自动下一步”。即终止的是 pilot 与后续投入，设计文档本身保留为已审查记录；三条线相互独立（`research-ledger.md` §2），一线终止不影响另外两条。

### 4.4 唯一活路与优先级

“需实测验证”是当前唯一未被关闭的通道。按性价比排序：

1. **EvilGenie 优先**：S1 已有文档支持；其“不改任务本体、只改评价环境与反馈”的做法与 `design.md` 的操纵要求最贴合。第一步做实测 1。
2. **RHB 其次**：必须先做实测 6 排除 §5 排除项；且 §2 明示不直接用其数据，即使通过，可复用的也只是底层任务与反馈形状。

两条路线都必须在已冻结的来源范围内完成；实测任何一条失败都不构成启用新来源的理由。

### 4.5 不得声称什么

- 不得把“EvilGenie / RHB 满足或不满足某条标准”写成已验证结论——本文只证明仓库内不存在任何验证记录。
- 不得把“存在需实测验证的来源”写成“该线大概率可行”；它只表示验证未完成。
- 不得把“该线已终止”写成事实——实测未做，终止是实测之后的可能分支。
- 不得把本文的推断（尤其 §2.2 关于编程任务单一聚合分数的推理）当作仓库记录的事实。
- 不得把本次差距分析当作放行依据：来源适配即使全部实测通过，也仍被隔离、呈现器、预检、动作采集等阻塞（`pre-test-readiness.md` §3）。

## 5. 开放问题（发现的设计缺口，本文不做修改）

1. **条数口径不一致**：本次核查的任务口径称“五条素材准入标准”，而 `source-selection.md` §4 实际记录六条（S1–S6）。建议后续维护时统一口径，避免核对时漏条；本文按六条执行。
2. **EvilGenie 底座来源未记录**：仓库只写“成熟 coding 任务作为底座”，没有记录底座是哪个 benchmark、哪个版本。实测 1 之前需要先确认底座身份，否则结果无法归档到冻结清单。
3. **RHB 的可运行性未记录**：§2 给出的是文章链接，仓库没有记录它是否附带可运行实现或仅有描述。实测 6 的第一步是确认存在可检查的任务与实现；若只有文字描述，RHB 实际上只够当方法参考，候选资格要重新评估。
4. **P/C 是否共用同一批母任务**：这是 `pre-test-readiness.md` §5 重大分支 4，仍开放。实测 3 建议同时收集两个模块的证据，避免重复劳动；但分支选择本身不在本文作出。
5. **规模不足时的处理**：`design.md` §8 写明“不足 8 个有效母任务时只报告执行协议未完成，不套用 6/8 继续门槛”。若实测 8 发现合格任务只有 1–2 个，是按协议未完成处理、还是触发部分终止，需要一次明确的分支决定，本文不代答。
6. **受控权重与原生价值的边界**：`research-ledger.md` 4.3 与 `design.md` §3.1 要求 v0 受控 3:1 权重与来源原生价值分开。实测时若发现来源自带原生权重或核心测试比例，必须单列记录、不与受控权重块混合，此点在实测记录格式中尚无模板。
