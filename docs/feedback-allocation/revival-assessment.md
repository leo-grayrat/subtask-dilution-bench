## 1. 路径 A：一轮导向型全网搜索

### 1.1 搜索口径

按用户指定，本轮不是再找一遍和 RHB 类似的东西，而是导向型搜索：找天然带子项分或多组件加权评分的真实任务环境（只有这类环境才可能承载 3:1 价值权重操纵），且任务必须是多步持续工作而非单问单答。准入标准按 source-selection.md 第 4 节的六条（S1 至 S6）加 design.md 补充条款（D1 至 D6）执行；判定标签沿用三级：文档证据满足 / 文档证据不满足 / 证据不足需实测。搜索覆盖四个方向：多检查点基准（TheAgentCompany 类）、多目标软件工程（multi-issue 或多目标 SWE 类）、带分项 rubric 的真实工作流基准、CI 驱动的多组件任务。访问日期均为 2026-08-26。

### 1.2 候选一：TheAgentCompany（CMU，arXiv:2412.14161）

出处：https://github.com/TheAgentCompany/TheAgentCompany（MIT 许可，论文 arXiv:2412.14161）。175 个真实职场任务（软件工程、项目管理、数据科学、行政、人力、财务），自托管开源服务栈（GitLab、OwnCloud、Plane、RocketChat），任务由在职领域专家人工设计（论文附录 B：69 个 SWE 任务由十名在职工程师参与出题）。

结构证据（论文正文加本仓库 .materials-cache/round4/ 已缓存的评分器源码，后者为稀释线第四轮合法下载，本轮未重复下载）：

- 每任务含带分值的检查点组加逐检查点的程序化评估器（论文第 4 节原文：Tasks are divided into checkpoints representing intermediate milestones, each assigned a point value）。
- 评分架构：base/scoring.py 的 Result 类接受可插拔的 scoring_strategy，默认对检查点求和；每个检查点是独立确定性 Python 函数，读取环境状态（工作区文件、内网服务、聊天记录）评分。
- 分值权重天然不均：已缓存的 admin-employee-info-reconciliation.checkpoints.md 为 3 分加四个 1 分共 7 分；finance-create-10k-income-report 为 1 加 1 加 1 加 2 加 1 共 6 分。即加权子项分是该来源的原生结构，不是我们外加的。

逐条对照六标准：

| 标准 | 判定 | 证据 |
|---|---|---|
| S1 外部可验证整体目标 | 文档证据满足 | 评分由逐检查点程序化评估器对环境状态执行，可重放；自托管环境可重置（论文第 3、4 节） |
| S2 拆成两个竞争资源的部分 | 文档证据满足（任务级待实测） | 检查点组覆盖数据加工、表格产物、对外沟通等不同工作成分，各自需要多步操作且共享同一预算；哪些任务的两个成分构成真实取舍须按 design.md 3.2 节预算稀缺性预检逐题判定 |
| S3 支持一种冻结模块 | 文档证据不满足（原生）；可通过操纵层承载，见第 2 节 | 论文未描述任何运行中的环境侧周期反馈；评估在任务结束时执行（论文 4.2 节三阶段工作流），反馈通道不存在，与 EvilGenie 同型缺口 |
| S4 记录 tokens、tool calls、迭代 | 文档证据满足 | 官方基线 OpenHands 记录完整轨迹；论文按 steps 与 cost 报告（4.1 节）；动作到 F、C、B 的归属标注需自建代码本 |
| S5 同一任务强弱反馈配对 | 同 S3：原生不满足，需操纵层 | 同一母任务四个条件共享同一初始状态与评分代码在架构上成立（任务是可重置的初始化脚本），反馈呈现差异须由中间层实现 |
| S6 高低价值局部都能构造 | 文档证据满足（待实测等价重加权） | 检查点分值即外部评分权重；scoring_strategy 可插拔意味着两份价值映射可落到同一评分代码（注入加权聚合策略）而非只改提示词；两份映射总可得分相同须在冻结时逐题验证（D5） |

判定：六条中 S1、S2、S4、S6 达文档证据满足级（各带括号内实测前提），S3、S5 原生不满足。这是本轮唯一越过四条硬标准的候选。其缺的 S3、S5 恰是反馈操纵层要补的部分，且 design.md 第 4、5 节的呈现器与信息等价预检本来就是为该缺口设计的规格。

跨线复用说明：TheAgentCompany 已在稀释线 9 题候选池内（candidate-config-draft-v0.md 题 2 与备位），用户已批准不同被测模型下的跨线复用；复用同一来源不等于复用同一实验设计或共享总分（总账第 2 节）。

### 1.3 候选二：OSWorld 2.0（arXiv:2606.29537）

出处：arXiv:2606.29537（2026-06-28 提交，v2 2026-07-13），108 个长程计算机使用工作流，人类完成中位数约 1.6 小时、平均 318 次工具调用。论文 2.1.3 节（原文）：OSWorld 1.0 uses binary pass/fail scoring... We therefore use fine-grained partial rewards with task-specific checkpoints, averaging 27.25 checkpoints per task，且对终局环境状态按全部检查点评分而非固定顺序。这是本轮搜到的分项粒度最高的环境。

逐条对照：S1 文档证据满足（执行式状态评估）；S2 结构上满足且粒度最细（均 27.25 检查点，待任务级实测）；S3、S5 原生不满足（同型：无运行中环境侧反馈通道）；S4 满足（全轨迹记录）；S6 检查点加权可构造（待实测）。

但有一条致命未决项：代码与任务数据的公开可获取状态未确认。官网 os-world.github.io 截至访问日仍展示 OSWorld 1.0（369 任务）；github.com/xlang-ai/OSWorld2 不存在（404）；论文摘要与页面未给出已发布的仓库链接。按本文证据规则，公开可获取性未确认的来源不能进入候选池。判定：结构合格、可得性未确认，不进入本轮候选；登记为复检触发条件（见 1.7 节）。

### 1.4 候选三：WorkArena / WorkArena++（ServiceNow，ICML 2024）

出处：https://github.com/ServiceNow/WorkArena。682 个 ServiceNow 知识工作任务。第三方综述（arXiv:2603.22744，2026-03）明确记录（原文）：WorkArena evaluates 682 tasks in ServiceNow, the closest existing enterprise benchmark, but uses binary completion metrics。S2、S6 文档证据不满足（二值完成度，无子项分可挂权重）；另需第三方托管实例（依赖外部账号与实例申请）。判定：规则层面不合格（触发 source-selection.md 第 5 节只有一个最终分数的排除形状）。

### 1.5 候选四：AgentBoard（进度率指标框架）

出处：AgentBoard 提供子目标完成比例的 progress rate 指标。不合格原因：progress rate 是叠加在既有环境（AlfWorld、WebShop、Jericho 等）上的测量口径，不是进入外部评分的权重；其底层环境多为合成或游戏类，不符合总账原则 3 的真实数据源要求；且子目标标注是测量层而非任务原生的可交换评分结构，不满足 D5。判定：规则层面不合格。

### 1.6 其余搜索方向的结果（空或不合格）

- 多目标软件工程方向：本轮未发现任何公开的单一任务多 issue 或多目标 SWE 基准。Multi-SWE-bench、SWE-PolyBench、OmniGIRL、SWE-rebench 等（见 Awesome-Issue-Solving 清单，github.com/ZhonghaoJiang/Awesome-Issue-Solving）均为单 issue 形态加通过或失败的二值判定，与 EvilGenie 底座同型：无子项分、无价值交换落点。判定：该方向本轮为空。
- rubric 分项的真实工作流基准：除 TheAgentCompany 与 OSWorld 2.0 外，未发现新的合格公开出处。财富管理等工作流基准（arXiv:2512.02230）自述沿用 TheAgentCompany 式检查点部分得分，且为极新预印本、实现公开状态未核实，不构成独立候选（推测：其检查点机制与 TAC 同型）。
- CI 驱动方向：未发现直接候选。Terminal-Bench 已在稀释线第四轮做过题目级分析（241 个 task.yaml 全量在手）：其评分为隐藏测试套件，终局执行、无原生子项加权结构，对反馈线同样触发单分数排除形状；不重复展开。
- AppWorld（ACL 2024，可控应用世界）：本轮检索未取得其多组件加权评分的可用证据，按证据规则不判定、不纳入。
- τ2 与 ALE 的跨线复核：τ2 的分项评价器（ENV、COMMUNICATE、ACTION、NL 断言）最终奖励是各分量相乘（已缓存源码 tau2/evaluator/evaluator.py 的 EvaluationType 注释：The final reward is the product of all applicable component rewards）。乘法聚合意味着任一分量为零则总奖励为零，不存在设计要求的合法局部低价值取舍空间，且无运行中反馈通道。判定：τ2 不适合反馈线。ALE 为单一产物数值精确比对（单分数形态），同样不适合。两者不进入候选。

## 2. 路径 B：操纵层方案评估

### 2.1 价值操纵：检查点权重重分配是否仍符合 design.md 3.1 节

逐字对照设计条款（design.md 第 3.1 节原文要点）与本方案的对应：

- 条款：同一母任务建立两份价值映射，并把映射同时写进任务目标和外部 evaluator。本方案：把母任务的检查点划分为焦点组 F 与竞争组 C，两份映射分别为 F 组权重高、C 组权重低与反之；权重进入评分聚合函数，同时写进任务说明。对应成立。
- 条款：第一轮因果实验明确采用受控、公开且真正进入外部评分的权重，推荐 w_H 比 w_L 等于 3 比 1。本方案：3 比 1 施加于检查点组的聚合权重。技术落点已实证存在：base/scoring.py 的 Result 接受自定义 scoring_strategy（默认求和），注入加权策略即可，检查点判定函数本身不改。对应成立。
- 条款：价值映射必须对被测 agent 可知。本方案：组权重写入任务说明，可公开。对应成立。
- 条款：高低的差别必须真正改变外部得分，不能只在提示词里说某项重要。本方案：权重在评分聚合代码中执行，不是提示词声明。对应成立，且恰好避免了 source-selection.md 第 5 节明令禁止的人工声明局部不重要的替代方案。
- 条款：两份映射的总可得分必须相同，背景工作权重不变。本方案：可实现（同组内分值不变、只交换组间系数并归一化），但必须逐题验证，属冻结清单第 4 项，此处不作已验证结论。
- 条款：母任务只有在两个目标允许这种等价重加权时才能进入 v0。本方案：等价重加权是检查点聚合层的纯算术操作，架构上总是允许；真正的门槛不在权重而在 F、C 是否构成本来就有的真实工作要求，这由 2.2 节的任务级筛选承担。

结论：价值操纵条款逐字符合。与 EvilGenie 被否决的理由（无多分项评分、引入权重必须先新造子项评分，等于重建 evaluator）有本质区别：TheAgentCompany 原生就有分项评分与权重机制，本方案只在其既有机制内重分配权重，不新造子项评分。

### 2.2 反馈操纵与工程落地

反馈操纵需要四个组件，全部需新建（第 1.7 节已证没有任何候选原生提供）：

1. 周期重评分器：复用 TheAgentCompany 原生逐检查点评分函数（各检查点是读环境状态的确定性函数，无副作用，可反复调用），在被测会话进行中按固定节点触发，产出分项子得分。含 LLM 判定检查点的任务（如用模型评估聊天记录的检查点）需排除该类检查点或实测其重复调用稳定性，此处不作已验证结论。
2. 规范载荷生成器：把子得分结果转成两种信息等价的呈现形式（P 模块），或同序列不同时机的评价流（C 模块）。
3. 注入通道：把反馈送入被测会话，注入点在 harness 层、对被测代理不可见。注意这是新建反馈通道，不是复用原生通道——原生通道不存在。
4. 动作级计数器：记录 tokens、tool calls、迭代次数并按代码本归属到焦点工作、竞争工作、背景工作（对应 S4 的自建代码本残留项）。

P 模块呈现方式：同一规范载荷，弱呈现为周期报告中固定位置的普通状态行，强呈现为报告首位的独立标题与状态符号；两份报告须过信息等价预检（内容相同、长度差控制在设计允许范围）。对应 design.md 第 4 节规格。

C 模块呈现方式：同一评价序列只改在线可见时机——连续条件在每个周期重评分后立即给出子得分，批量条件在会话结束统一给出；以中性回执保持两种条件的消息节奏一致。对应 design.md 第 5 节规格。

最易承载环境：TheAgentCompany。理由：检查点评分函数确定性、无副作用、可重复调用；环境可通过初始化脚本重置；官方 OpenHands 基线提供 harness 骨架。服务栈需 Docker（GitLab、OwnCloud、Plane、RocketChat，镜像体量约 30GB 量级），这是工程成本而非结构障碍。

### 2.3 漂移自检（必答）

逐条对照 archive/failed-design/README.md 记录的两种失败模式。

失败模式一：问题漂移。判定：未发生。本方案一字未改研究问题——仍是在有限预算下，反馈的分配方式如何影响代理对不同价值目标之间的资源分配。2 乘 2 设计、3 比 1 受控权重、机会成本指标、预算稀缺性预检、停止规则全部保留。操纵层改变的只是反馈的实施载体，而 design.md 第 4、5 节本来就把呈现器定义为实验组件；本方案是实施既有设计条款，不是替换研究问题。

失败模式二：被现有 benchmark 形式牵着走。判定：方向相反，但须说明区别何在。被形式牵着走的表现是：因为基准有某种形式，就把研究问题改成测那个形式。本方案的表现是：为了测原研究问题，必须让载体具备子项加权评分与环境可重置两种能力，任务本体（目标、初始状态、检查点判定函数）一律不改，只加设计已明文规定的两类操纵（权重重分配、呈现形式）。筛选权仍在研究侧：F、C 成分不构成真实取舍的任务在预检即淘汰。

两个真实残留漂移风险，如实列出：

1. 操纵层注入的反馈由自建代码生成，若反馈措辞、节奏本身引导代理，测到的将是提示引导而非反馈分配。防线：信息等价预检、中性措辞、呈现模板冻结；防线非完美，故进入 2.4 节不得声称清单。
2. 检查点的组划分（哪些归焦点、哪些归竞争）由我们做；若分组不对应真实工作成分，价值操纵退化为纯算术操作。防线：逐题人工审查加预算稀缺性预检。这也解释了为什么 TAC 分值天然不均仍不能免检。

漂移自检结论：通过。测的仍是原研究问题；两个残留风险以预检与不得声称清单承接；未为救活此线放宽任何标准。

### 2.4 不得声称清单

若本方案实施，结论阶段不得声称以下任何一条（依据 design.md 第 14 节结论边界与总账证据同宽原则）：

1. 不得声称测到了真实工作环境中的反馈分配——反馈通道是操纵层新建的，不存在于任何真实工作场所；可声称的上限是：受控呈现与时机条件下，周期性分项评分反馈的分配效果。
2. 不得声称同时得到 P 模块与 C 模块的结论——按第 3 节条件仅 C 模块先行时，P 模块结论不成立。
3. 不得声称结论可推广到未通过预检的任务或其他基准。
4. 不得声称 3 比 1 的结果可推广到其他权重比。
5. 不得声称操纵层的呈现措辞零引导——信息等价是预检项，不是默认事实。
6. 不得声称 LLM 判定类检查点的重复评分稳定——该项未实测。

### 2.5 工程前提（依赖如实标注）

1. 隔离前置（比全项目任何方案都更严）：被测代理必须收到操纵层注入的反馈，同时不可见操纵层代码、权重映射与重评分器。注入点须在 harness 消息边界，被测会话上下文与操纵层进程分离。隔离本身是全项目未解决的共同阻塞（见稀释线隔离边界实测记录）；在本方案下它是先决条件，隔离不落地则方案不可执行。
2. 运行环境：TheAgentCompany 需 Docker 服务栈（GitLab、OwnCloud、Plane、RocketChat，镜像约 30GB 量级）；本机当前无 Docker 与 WSL，须另行搭建，本机不可直接实测。
3. 工程量：操纵层需新建呈现器、周期重评分器、注入通道与动作级计数；估计需要二十个以上开发会话（推测，非承诺，未经实施验证）。
4. 跨线关系：与稀释线复用同一来源已获用户批准（不同被测模型）；若两线冻结同一任务，检查点版本快照可共享，实验设计与总分互不共享（总账第 2 节）。
